1Authentification ou autorisation

Les deux mots se ressemblent, mais ils répondent à deux questions différentes, posées à deux moments différents.

AuthentificationAutorisation
La questionQui êtes-vous ?Qu'avez-vous le droit de faire ?
Quandune fois, à la connexion (puis on garde une preuve : session ou jeton)à chaque requête, pour chaque action
Commentmot de passe, fournisseur d'identité (Keycloak, Entra ID, Google…), clé d'accèsrôles (admin, customer), permissions (delete:Product), règles sur la ressource
Échec côté HTTP401 Unauthorized : pas (ou plus) authentifié, malgré son nom403 Forbidden : authentifié, mais pas autorisé
Dans cette pagesections 2 à 5sections 6 et 7

Les deux statuts ont été observés sur l'API de démonstration. Connectée en alice, une suppression de produit répond 403 avec {"error": "Réservé au rôle admin"}. Après un redémarrage du serveur, qui efface les sessions en mémoire, un clic sur « Supprimer » en admin reçoit 401, et l'application renvoie vers la page de connexion.

La règle d'or : c'est le serveur qui décide

Tout le code Angular s'exécute dans le navigateur de l'utilisateur. Il peut le lire, le modifier dans les outils de développement, ou ignorer l'application et appeler l'API directement avec curl. Un guard qui bloque une route, un bouton masqué pour un rôle : ce sont des choix d'ergonomie, pour ne pas montrer ce qui échouerait. La sécurité est ailleurs : le serveur vérifie l'identité et les droits à chaque requête, comme s'il n'y avait pas de front-end.

L'expérience le montre. Dans l'application, alice ne voit aucun bouton « Supprimer ». Depuis la console du navigateur, elle envoie quand même la requête, avec le bon en-tête XSRF (expliqué en section 5) :

const x = document.cookie.split('=')[1];
await fetch('/api/products/1', { method: 'DELETE', headers: { 'X-XSRF-TOKEN': x } });
// -> 403 { "error": "Réservé au rôle admin" }

Le produit n'est pas supprimé, parce que le serveur applique lui-même la règle « écriture réservée au rôle admin » (section 7). Sans cette vérification côté serveur, masquer le bouton n'aurait rien protégé.

À retenir Authentification = qui vous êtes (401 si inconnu) ; autorisation = ce que vous pouvez faire (403 si interdit). Le serveur vérifie les deux à chaque requête. Guards et boutons masqués côté Angular servent l'ergonomie, pas la sécurité.

2Le jeton : anatomie d'un JWT

Après l'authentification, le client garde une preuve qu'il renvoie à chaque requête. Cette preuve prend deux formes : un identifiant de session opaque (une chaîne aléatoire, qui ne veut rien dire hors du serveur qui l'a créée), ou un JWT (JSON Web Token), qui contient lui-même les informations. Le JWT est le format qu'on rencontre partout, en particulier avec les fournisseurs d'identité de la section 4 ; il faut savoir le lire.

Trois parties séparées par des points

Un JWT s'écrit header.payload.signature. Les deux premières parties sont du JSON encodé en base64url (une variante de base64 sans +, / ni =, sûre dans une URL). Le jeton ci-dessous a été produit par un petit script Node de démonstration, signé avec une clé de test.

Lisible par tout le monde : signé, pas chiffré

Le base64url est un encodage, pas un chiffrement : n'importe qui lit le contenu, sans aucune clé. Dans la console du navigateur, une ligne suffit.

JSON.parse(atob(jwt.split('.')[1]))
// -> { sub: "alice", roles: ["customer"], iat: 1792000000, exp: 1792000900 }

atob décode du base64 classique : il suffit ici parce que ce payload ne contient ni - ni _. Dans le cas général, on remplace d'abord - par + et _ par /.

Ce que garantit la signature, c'est l'intégrité : si quelqu'un remplace "customer" par "admin" dans le payload, la signature ne correspond plus et le serveur rejette le jeton. Le script de démonstration fait l'essai et affiche original valide : true / falsifié valide : false. On en tire une règle : on ne met jamais de secret dans un payload (mot de passe, numéro de carte, donnée personnelle sensible).

Les claims à connaître

Les champs du payload s'appellent des claims. Quelques noms courts sont standardisés ; les autres, comme roles, sont propres à chaque fournisseur.

ClaimSensDans l'exemple
subsubject : l'identifiant de l'utilisateur"alice"
expdate d'expiration, en secondes depuis 1970 ; au-delà, le jeton est refusé1792000900 = 2026-10-14 18:01:40 UTC
iatissued at : date d'émission1792000000, soit 15 minutes avant exp
iss, audqui a émis le jeton, et pour quelle API il est fait ; le serveur doit les vérifierabsents ici
rolesclaim non standard : chaque fournisseur a le sien (Keycloak : realm_access.roles)["customer"]

Access token et refresh token

Un JWT ne se révoque pas facilement : le serveur le croit tant que la signature est bonne et que exp n'est pas passé. On lui donne donc une vie courte, et on en distribue deux sortes.

Access tokenRefresh token
Rôleaccéder à l'APIobtenir un nouvel access token sans redemander le mot de passe
Durée de viecourte : 5 à 15 minuteslongue : heures ou jours, souvent à usage unique (rotation)
Envoyé àl'API, à chaque requêteuniquement au point d'entrée de renouvellement
Révocationen pratique, on attend exppossible côté serveur (il est enregistré)
Où le garder dans une SPAen mémoiredans un cookie httpOnly (section 3)

Le format du jeton (JWT ou identifiant opaque) et l'endroit où on le garde sont deux questions distinctes. L'API de démonstration utilise un identifiant opaque dans un cookie : le navigateur ne voit jamais de JWT, et pourtant tout fonctionne.

À retenir Un JWT = header.payload.signature en base64url. Tout le monde peut le lire, seul le serveur peut le signer : signé, pas chiffré, donc aucun secret dedans. sub = qui, exp = jusqu'à quand. Access token court + refresh token long et révocable.

3Où garder le jeton

C'est la décision qui pèse le plus sur la sécurité d'une application front, et beaucoup de projets v20 l'ont prise par défaut : localStorage.setItem('token', …), puis un intercepteur qui recopie le jeton dans Authorization: Bearer. Le problème tient en une phrase : tout script qui s'exécute dans la page peut lire localStorage. Une seule faille XSS (cross-site scripting : un script étranger qui s'exécute dans votre page, via une dépendance npm compromise, un HTML injecté ou un script tiers) et le jeton part sur le serveur de l'attaquant, qui l'utilise ensuite depuis n'importe où, jusqu'à son expiration. Le message de cette section : on arrête les jetons dans localStorage.

Les cinq options, comparées

Le tableau compare les emplacements possibles selon cinq critères. « Vol par XSS » veut dire : un script injecté peut-il lire le jeton et l'emporter ? « Exposition CSRF » (cross-site request forgery, qu'Angular appelle XSRF) : un autre site peut-il faire envoyer une requête authentifiée par le navigateur, à l'insu de l'utilisateur ? « Autre origine » : l'API est-elle appelable si elle n'a pas le même protocole, domaine et port que l'application ?

Une nuance honnête : un cookie httpOnly empêche le vol du jeton, pas l'exécution d'un script XSS. Pendant que la page est ouverte, ce script peut encore appeler l'API au nom de l'utilisateur. Il ne peut simplement plus emporter le jeton pour s'en servir ailleurs et plus tard. La défense contre la XSS elle-même reste l'échappement automatique d'Angular, une CSP (Content Security Policy, l'en-tête qui dit au navigateur quels scripts il a le droit d'exécuter) et des dépendances surveillées.

La recommandation

  • Par défaut : un cookie httpOnly, Secure, SameSite=Strict (ou Lax), posé par le serveur, avec une protection CSRF par jeton XSRF en double submit (section 5). Angular n'a rien à stocker.
  • Avec un fournisseur d'identité (section 4) : un BFF. Le BFF mène le dialogue OAuth avec le fournisseur, garde les jetons côté serveur et ne donne au navigateur qu'un cookie de session httpOnly. Le front-end Angular est alors exactement celui de cette page.
  • Si l'architecture impose une SPA qui tient elle-même ses jetons : l'access token en mémoire, à durée courte, et le refresh token dans un cookie httpOnly limité au chemin de renouvellement. Au démarrage (ou après F5), un appel au point de renouvellement redonne un access token. C'est le compromis acceptable ; localStorage ne l'est pas.

Le parcours, avec un cookie httpOnly

Le schéma suit les échanges observés sur l'application de démonstration. Le navigateur et l'API sont sur la même origine (http://localhost:4380), grâce au proxy de développement d'Angular présenté plus bas : c'est ce qui permet SameSite=Strict.

Côté serveur : poser le cookie

L'API de démonstration est json-server 0.17.4 utilisé comme un module Express : on garde son routeur pour /api/products et on ajoute nos propres routes /auth. Un petit middleware, placé avant toutes les routes, lit l'en-tête Cookie dans req.cookies et retrouve la session correspondant au cookie sid dans req.session (une Map en mémoire). La connexion vérifie les identifiants de démonstration, crée un identifiant de session aléatoire, et le confie au navigateur avec res.cookie. Trois options de sécurité font le travail : httpOnly le cache à JavaScript, secure le réserve à HTTPS (le navigateur considère localhost comme sûr, ce qui permet de tester en HTTP), sameSite: 'strict' interdit de l'envoyer depuis un autre site.

api/server.cjs
server.post('/auth/login', (req, res) => {
  const { username, password } = req.body ?? {};
  const user = DEMO_USERS[username];
  if (!user || user.password !== password) {
    return res.status(401).json({ error: 'Identifiants invalides' });
  }
  const sid = crypto.randomBytes(24).toString('hex');
  sessions.set(sid, { username, roles: user.roles });
  // le cookie de session : illisible en JavaScript, jamais envoyé depuis un autre site
  res.cookie('sid', sid, { httpOnly: true, secure: true, sameSite: 'strict', path: '/', maxAge: 30 * 60 * 1000 });
  // le jeton XSRF : lisible en JavaScript, exprès, pour qu'Angular le recopie dans un en-tête
  res.cookie('XSRF-TOKEN', crypto.randomBytes(16).toString('hex'), { secure: true, sameSite: 'strict', path: '/' });
  res.json({ username, roles: user.roles });
});

server.get('/auth/me', (req, res) => {
  if (!req.session) return res.status(401).json({ error: 'Non authentifié' });
  res.json(req.session);
});

En développement, Angular et l'API tournent sur deux ports, donc deux origines. Le proxy du serveur de développement d'Angular les réunit : le navigateur ne parle qu'à localhost:4380, qui transmet /auth et /api à l'API. Le fichier est déclaré dans angular.json, option proxyConfig de la cible serve. En production, un reverse proxy (ou le BFF) joue le même rôle.

  "/auth": { "target": "http://localhost:3101", "secure": false },
  "/api": { "target": "http://localhost:3101", "secure": false }

4OIDC, OAuth2 et PKCE : les fournisseurs d'identité

Dans une entreprise, l'application n'a souvent pas sa propre table de mots de passe : elle délègue la connexion à un fournisseur d'identité (Keycloak, Microsoft Entra ID, Auth0, Okta, Google…). Deux standards encadrent ce dialogue. OAuth 2 sert à obtenir un access token pour appeler une API. OpenID Connect (OIDC) ajoute par-dessus la question « qui est l'utilisateur ? », avec un ID token (un JWT) qui le décrit.

Le flux Authorization Code avec PKCE

Pour une application qui tourne dans le navigateur, le seul flux recommandé aujourd'hui est Authorization Code avec PKCE (Proof Key for Code Exchange). L'ancien flux implicit, qui renvoyait le jeton directement dans l'URL, est abandonné. Le principe de PKCE : l'application invente un secret à usage unique avant de partir, et devra le présenter pour échanger le code.

  1. L'application génère un code_verifier aléatoire et en calcule l'empreinte, le code_challenge (SHA-256).
  2. Elle redirige l'utilisateur vers la page de connexion du fournisseur, avec le code_challenge.
  3. L'utilisateur se connecte chez le fournisseur : l'application ne voit jamais son mot de passe.
  4. Le fournisseur redirige vers l'application avec un code à usage unique dans l'URL.
  5. L'application échange code + code_verifier contre les jetons. Un code intercepté ne sert à rien sans le code_verifier.

Qui mène ce dialogue ? Soit la SPA elle-même, avec une des bibliothèques ci-dessous, et les jetons vivent dans le navigateur ; soit un BFF, qui fait l'échange côté serveur et ne rend qu'un cookie httpOnly : c'est l'option la plus sûre, et côté Angular on retrouve alors exactement le code de la section 5.

5Côté Angular : session, intercepteur, XSRF

Avec un cookie httpOnly, le travail d'Angular change de nature : il n'a plus de jeton à stocker ni à recopier. Il lui reste quatre tâches, traitées dans l'ordre : savoir qui est connecté, retrouver cette information au démarrage, réagir quand le serveur dit « session expirée », et envoyer le jeton XSRF sur les requêtes qui modifient.

La session dans un signal

Ce que l'application doit savoir de l'utilisateur tient dans une interface : son nom et ses rôles, tels que le serveur les renvoie. Le même fichier déclare les actions et les sujets que l'autorisation manipulera en section 7.

src/app/auth/session.ts
// Ce que le serveur renvoie sur GET /auth/me : QUI est connecté, et avec quels rôles.
export interface Session {
  username: string;
  roles: string[];
}

export type Action = 'read' | 'edit' | 'delete';
export type Subject = 'Product';

Le service AuthService garde cette session dans un signal privé et n'expose qu'une version en lecture seule, plus un computed isLoggedIn. Le point important est la source de la session : la réponse de GET /auth/me ou de POST /auth/login, jamais la lecture d'un jeton côté client. Un JWT décodé dans le navigateur peut être périmé, révoqué ou modifié ; la réponse du serveur, elle, reflète la session réelle.

src/app/auth/auth.service.ts
@Injectable({ providedIn: 'root' })
export class AuthService {
  private readonly http = inject(HttpClient);
  private readonly router = inject(Router);
  // ...
  // la session vient du SERVEUR (GET /auth/me), jamais de la lecture d'un jeton
  private readonly _session = signal<Session | null>(null);
  readonly session = this._session.asReadonly();
  readonly isLoggedIn = computed(() => this._session() !== null);

  // appelé au démarrage (provideAppInitializer) : le cookie httpOnly suffit à retrouver la session après F5
  async loadSession(): Promise<void> {
    try {
      this.setSession(await firstValueFrom(this.http.get<Session>('/auth/me')));
    } catch {
      this.setSession(null); // 401 : personne n'est connecté
    }
  }

  async login(username: string, password: string): Promise<void> {
    // la réponse pose le cookie httpOnly ; le corps ne contient AUCUN jeton
    this.setSession(await firstValueFrom(this.http.post<Session>('/auth/login', { username, password })));
  }

  async logout(): Promise<void> {
    await firstValueFrom(this.http.post('/auth/logout', {}));
    this.setSession(null);
    await this.router.navigateByUrl('/login');
  }

  // appelé par l'intercepteur quand le serveur répond 401
  clear(): void {
    this.setSession(null);
  }

Retrouver la session au démarrage

Après F5, le signal repart à null, mais le cookie est toujours là. provideAppInitializer appelle loadSession() et Angular attend la promesse avant la première navigation : les guards de la section 6 connaissent donc déjà la session quand ils s'exécutent. Sans cette attente, un F5 sur une page protégée renverrait vers la connexion alors que l'utilisateur est connecté.

src/app/app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideRouter(routes),
    provideHttpClient(
      withInterceptors([authInterceptor]),
      // valeurs par défaut, écrites ici pour les voir : le cookie lu, l'en-tête envoyé
      withXsrfConfiguration({ cookieName: 'XSRF-TOKEN', headerName: 'X-XSRF-TOKEN' }),
    ),
    // ...
    // avant la première navigation : GET /auth/me, pour que les guards connaissent déjà la session
    provideAppInitializer(() => inject(AuthService).loadSession()),
  ],
};

L'intercepteur : cookies et 401

L'intercepteur fonctionnel a deux rôles. Il pose withCredentials: true sur chaque requête : derrière le proxy, ce n'est pas nécessaire (même origine), mais si l'API est sur une autre origine, c'est ce qui demande au navigateur de joindre les cookies. Le serveur doit alors répondre avec CORS (Cross-Origin Resource Sharing, les en-têtes par lesquels une API autorise une autre origine) : Access-Control-Allow-Credentials: true et une origine explicite dans Access-Control-Allow-Origin, jamais *. Et SameSite continue de s'appliquer : un cookie Strict ne part pas vers un autre site. Et il traite le 401 d'un appel métier comme une session expirée : il vide la session et renvoie vers /login en gardant la page courante dans returnUrl. Les appels à /auth/ sont exclus, sinon un mauvais mot de passe (401 aussi) déclencherait une redirection.

src/app/auth/auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);
  const auth = inject(AuthService);

  // withCredentials : le navigateur joint les cookies même si l'API est sur une autre origine
  // (inutile derrière le proxy de dev, indispensable si l'API est sur api.example.com)
  return next(req.clone({ withCredentials: true })).pipe(
    catchError((err: unknown) => {
      // 401 sur un appel métier = session expirée : on vide la session et on renvoie vers /login
      if (err instanceof HttpErrorResponse && err.status === 401 && !req.url.startsWith('/auth/')) {
        auth.clear();
        router.navigate(['/login'], { queryParams: { returnUrl: router.url } });
      }
      return throwError(() => err);
    }),
  );
};

L'intercepteur injecte AuthService, qui injecte lui-même HttpClient : il n'y a pas de dépendance circulaire, car un intercepteur fonctionnel n'est exécuté (et ses inject() résolus) qu'au moment d'une requête.

XSRF : le double submit

Un cookie part automatiquement, y compris sur une requête déclenchée par un autre site : c'est le risque CSRF (Angular dit XSRF, c'est la même chose). SameSite=Strict le bloque déjà dans les navigateurs récents ; le jeton XSRF ajoute une seconde barrière. Le serveur pose un deuxième cookie, XSRF-TOKEN, volontairement lisible par JavaScript. Sur chaque requête qui modifie (POST, PUT, DELETE…), Angular recopie sa valeur dans l'en-tête X-XSRF-TOKEN, et le serveur vérifie que les deux sont égaux. Un autre site peut faire partir le cookie, mais il ne peut pas le lire, donc pas écrire l'en-tête.

Angular fait la recopie tout seul, avec les noms par défaut XSRF-TOKEN et X-XSRF-TOKEN ; withXsrfConfiguration, vu plus haut dans app.config.ts, permet de les changer. Côté serveur, la vérification tient en quelques lignes, appliquée à la déconnexion et aux écritures sur /api.

api/server.cjs
// double submit : sur toute requête qui modifie, l'en-tête X-XSRF-TOKEN doit recopier le cookie XSRF-TOKEN
function checkXsrf(req, res, next) {
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();
  const cookie = req.cookies['XSRF-TOKEN'];
  if (!cookie || req.get('X-XSRF-TOKEN') !== cookie) {
    return res.status(403).json({ error: 'XSRF token manquant ou invalide' });
  }
  next();
}
// ...
server.post('/auth/logout', checkXsrf, (req, res) => {
  sessions.delete(req.cookies.sid);
  res.clearCookie('sid', { path: '/' });
  res.clearCookie('XSRF-TOKEN', { path: '/' });
  res.status(204).end();
});

Le jeton de la démonstration est une simple valeur aléatoire. L'OWASP recommande d'aller plus loin en production : un jeton signé par le serveur, ou lié à la session, pour qu'un sous-domaine compromis ne puisse pas poser son propre cookie XSRF-TOKEN.

Une limite à connaître, lue dans le code d'Angular 22.2 (xsrfInterceptorFn) : l'en-tête n'est ajouté que pour une requête qui n'est ni GET ni HEAD, et dont l'origine est celle de la page. Vers une API sur un autre domaine, Angular n'envoie pas l'en-tête : il faut alors un intercepteur maison, ou, plus simple, remettre l'API sur la même origine (proxy, BFF).

Connexion et déconnexion

La page de connexion reprend Signal Forms, vu au jour 2. L'action d'envoi appelle auth.login(), puis revient à la page demandée avant la redirection du guard, lue dans returnUrl.

src/app/pages/login.ts
readonly credentials = signal({ username: '', password: '' });
readonly f = form(
  this.credentials,
  (p) => {
    required(p.username);
    required(p.password);
  },
  {
    submission: {
      action: async (field) => {
        const { username, password } = field().value();
        try {
          await this.auth.login(username, password);
          // retour à la page demandée avant la redirection du guard
          await this.router.navigateByUrl(this.route.snapshot.queryParamMap.get('returnUrl') ?? '/');
        } catch {
          this.error.set('Identifiants invalides');
        }
      },
    },
  },
);

La déconnexion, déjà vue dans le service, appelle POST /auth/logout : le serveur supprime la session et efface les deux cookies. Vider le signal côté client ne suffirait pas, puisque le cookie httpOnly resterait valable.

6Les guards

Un guard est une fonction que le routeur appelle avant une navigation. Elle répond true (on continue), false (on reste), ou une redirection. Rappel de la section 1 : c'est de l'ergonomie, le serveur reste le seul juge. Le type de retour dans Angular 22 est MaybeAsync<GuardResult>, avec GuardResult = boolean | UrlTree | RedirectCommand : une valeur directe, une promesse ou un Observable.

Angular propose trois types de guards fonctionnels, un par question.

TypePosé dans la routeQuestion posée
CanActivateFncanActivatepeut-on afficher cette route ?
CanMatchFncanMatchcette route doit-elle même être retenue ? Si non, le routeur essaie la suivante, et un loadComponent n'est pas téléchargé
CanDeactivateFn<T>canDeactivatepeut-on quitter le composant T ?

CanActivateFn : connecté, sinon /login

Le premier guard lit isLoggedIn(). S'il n'y a personne, il renvoie un UrlTree vers /login, en gardant l'URL demandée : c'est ce returnUrl que relit la page de connexion.

src/app/auth/auth.guards.ts
// 1. connecté ou pas : sinon, redirection vers /login en gardant l'URL demandée
export const authGuard: CanActivateFn = (_route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);
  return auth.isLoggedIn() ? true : router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

On l'a vérifié dans le navigateur : sans être connecté, ouvrir /account mène à /login?returnUrl=%2Faccount ; après la connexion, on arrive sur /account.

Une fabrique de guards, CanMatchFn et RedirectCommand

Pour un guard qui dépend d'un paramètre (un rôle), on écrit une fabrique : une fonction qui reçoit le paramètre et renvoie le guard. roleGuard('admin') renvoie un CanMatchFn. Pour rediriger, il utilise RedirectCommand plutôt qu'un simple UrlTree : la classe existe dans les types de @angular/router 22.2.2 (constructor(redirectTo: UrlTree, navigationBehaviorOptions?: NavigationBehaviorOptions)) et permet de passer des options de navigation, ici skipLocationChange pour ne pas changer l'URL affichée.

src/app/auth/auth.guards.ts
// 2. une FABRIQUE de guard : roleGuard('admin') renvoie un CanMatchFn paramétré
export function roleGuard(role: string): CanMatchFn {
  return () => {
    const auth = inject(AuthService);
    const router = inject(Router);
    if (auth.hasRole(role)) return true;
    // RedirectCommand : une redirection AVEC options de navigation (ici, l'URL affichée ne change pas)
    return new RedirectCommand(router.parseUrl('/forbidden'), { skipLocationChange: true });
  };
}

Dans la configuration des routes, chaque guard se place sous sa clé. Pour /admin, canMatch est évalué avant loadComponent : sans le rôle, le fichier JavaScript de la page d'administration n'est jamais demandé au serveur.

src/app/app.routes.ts
export const routes: Routes = [
  { path: '', component: Home },
  { path: 'login', component: Login },
  { path: 'account', component: Account, canActivate: [authGuard] },
  {
    path: 'profile',
    component: ProfileEdit,
    canActivate: [authGuard],
    canDeactivate: [unsavedChangesGuard],
  },
  {
    path: 'admin',
    // canMatch AVANT loadComponent : sans le rôle, le chunk n'est même pas téléchargé
    canMatch: [roleGuard('admin')],
    loadComponent: () => import('./pages/admin-page').then((m) => m.AdminPage),
  },
  { path: 'forbidden', component: Forbidden },
// ...
];

Le navigateur confirme la différence entre les deux comptes. Le menu de l'application contient un lien « Admin » visible de tous ; on compare les fichiers JavaScript chargés avant et après un clic dessus.

CompteAffichéURLNouveau fichier JS

Nouveauté de la v22 : dans le type CanMatchFn, le troisième paramètre currentSnapshot devient obligatoire (changelog 22.0.0, avec une migration automatique). Un guard qui n'utilise pas ses paramètres, comme celui-ci, compile sans changement.

CanDeactivateFn : ne pas perdre une saisie

Le dernier guard regarde le composant qu'on quitte. On lui donne un contrat, l'interface HasUnsavedChanges, que le composant implémente : le guard ne connaît pas le composant, seulement la question qu'il sait poser.

src/app/auth/auth.guards.ts
// 3. quitter une page avec des modifications non enregistrées
export interface HasUnsavedChanges {
  hasUnsavedChanges(): boolean;
}
export const unsavedChangesGuard: CanDeactivateFn<HasUnsavedChanges> = (component) =>
  component.hasUnsavedChanges() ? confirm('Des modifications ne sont pas enregistrées. Quitter quand même ?') : true;

Le composant, lui, implémente ce contrat : il compare la saisie en cours à la dernière valeur enregistrée.

src/app/pages/profile-edit.ts
export class ProfileEdit implements HasUnsavedChanges {
  readonly bio = signal('');
  private readonly saved = signal('');

  save() {
    this.saved.set(this.bio());
  }

  // lu par unsavedChangesGuard avant de quitter la route
  hasUnsavedChanges(): boolean {
    return this.bio() !== this.saved();
  }
}

On l'a vérifié dans le navigateur, avec window.confirm remplacé dans la console pour répondre à la place de l'utilisateur : sur /profile, après la saisie « Bonjour », un clic sur « Accueil » affiche le message « Des modifications ne sont pas enregistrées. Quitter quand même ? » ; la réponse non laisse sur /profile, la réponse oui mène à /.

Reconnaître les anciens guards en classe

Dans un projet v20, on croise encore des guards écrits comme des classes qui implémentent CanActivate et que la route désigne par leur nom. Passer une classe (ou un InjectionToken) dans canActivate est déprécié depuis la v15.2 au profit des fonctions ; dans les types v22, ce cas porte le nom DeprecatedGuard, marqué @deprecated. Les interfaces CanActivate, CanMatch… restent exportées sans être dépréciées elles-mêmes : c'est la façon de les brancher qui l'est. Le code compile encore, ce qui explique qu'il survive.

src/app/auth/legacy-auth.guard.ts
// Le style d'avant la v15.2, encore courant dans le code v20 : une CLASSE qui implémente CanActivate,
// déclarée dans la route par son nom : canActivate: [LegacyAuthGuard]
@Injectable({ providedIn: 'root' })
export class LegacyAuthGuard implements CanActivate {
  private readonly auth = inject(AuthService);
  private readonly router = inject(Router);

  canActivate(): boolean | UrlTree {
    return this.auth.isLoggedIn() || this.router.parseUrl('/login');
  }
}

Pour migrer, on garde la logique et on la met dans une fonction CanActivateFn avec inject(), comme authGuard plus haut. De même, canLoad est déprécié depuis la v15.1 : canMatch le remplace.

À retenir Guards fonctionnels : CanActivateFn (afficher ?), CanMatchFn (retenir la route, et ne pas télécharger un fichier chargé à la demande), CanDeactivateFn (quitter ?). Rediriger avec un UrlTree, ou RedirectCommand pour passer des options de navigation. Un paramètre = une fabrique, roleGuard('admin'). Les classes passées par leur nom dans la route sont l'ancien style, déprécié.

7Autorisation : rôles, permissions, CASL

Une fois l'utilisateur connu, reste à décider ce qu'il peut faire. Deux modèles se rencontrent, souvent mélangés.

ModèlePrincipeExemple
RBAC (role-based access control)les droits découlent du rôleadmin peut supprimer un produit, customer peut le lire
ACL / règles par ressourceles droits dépendent aussi de la ressourceun client peut modifier ses commandes, pas celles des autres

Dans les deux cas, les rôles viennent du serveur, dans la réponse de /auth/me : c'est le champ roles de la session de la section 5.

hasRole() et can() dans le service

La première étape est de donner au reste de l'application deux questions simples. hasRole() teste un rôle ; can(action, sujet) teste une permission, déduite des rôles par une table. Les composants demandent « peut-on supprimer un produit ? » plutôt que « est-ce un admin ? » : le jour où un rôle editor apparaît, seule la table change.

src/app/auth/auth.service.ts
// RBAC écrit à la main : chaque rôle donne une liste de permissions "action:sujet"
const PERMISSIONS: Record<string, readonly string[]> = {
  customer: ['read:Product'],
  admin: ['read:Product', 'edit:Product', 'delete:Product'],
};
  // ...
  hasRole(role: string): boolean {
    return this._session()?.roles.includes(role) ?? false;
  }

  can(action: Action, subject: Subject): boolean {
    const roles = this._session()?.roles ?? [];
    return roles.some((role) => PERMISSIONS[role]?.includes(`${action}:${subject}`));
  }

Comme ces méthodes lisent le signal _session, un template qui les appelle se met à jour tout seul à la connexion et à la déconnexion.

Dans le template : @if plutôt qu'une directive

Deux écritures sont possibles. La première est une directive structurelle maison, *appIfRole, qui crée ou détruit le bloc selon le rôle ; un effect la relance quand la session change.

src/app/auth/if-role.directive.ts
// *appIfRole="'admin'" : affiche le bloc seulement si la session a ce rôle
@Directive({ selector: '[appIfRole]' })
export class IfRole {
  private readonly auth = inject(AuthService);
  private readonly template = inject(TemplateRef);
  private readonly container = inject(ViewContainerRef);
  readonly appIfRole = input.required<string>();

  constructor() {
    // effect : relancé quand la session (un signal) ou le rôle demandé changent
    effect(() => {
      this.container.clear();
      if (this.auth.hasRole(this.appIfRole())) {
        this.container.createEmbeddedView(this.template);
      }
    });
  }
}

La seconde n'ajoute rien : le contrôle de flux @if et une méthode du service. La page d'accueil montre les deux, plus une troisième forme, @if (can(...)), qui vient de CASL et sera présentée juste après.

src/app/pages/home.ts
<!-- 1. la directive structurelle maison -->
<p *appIfRole="'admin'"><a routerLink="/admin">Administration</a></p>
        <!-- ... -->
        <!-- 2. le contrôle de flux et une méthode du service : la forme à préférer -->
        @if (auth.can('edit', 'Product')) { <button type="button">Modifier</button> }
        <!-- 3. CASL, version signal -->
        @if (can('delete', 'Product')) { <button type="button" (click)="remove(p.id)">Supprimer</button> }

On préfère la forme @if (auth.can(...)). Elle n'a pas de directive à écrire, importer et tester ; elle accepte un @else ; elle parle de permission (can) plutôt que de rôle ; et la même expression sert ailleurs qu'en structure, par exemple [disabled]="!auth.can('edit', 'Product')", ce qu'une directive structurelle ne sait pas faire. La directive garde un intérêt si la même condition se répète partout et qu'on veut la nommer.

On l'a vérifié dans le navigateur : connectée en alice, la page d'accueil affiche les trois produits, sans lien « Administration » ni bouton « Modifier » ou « Supprimer ». En admin, le lien apparaît, et chaque produit porte les deux boutons.

CASL : les règles définies une fois

Quand les règles se multiplient, et surtout quand elles dépendent de la ressource (« ses propres commandes »), une table maison devient fragile. CASL est la bibliothèque de référence : on décrit les capacités une fois, puis on pose partout la même question, can(action, sujet). Deux paquets, vérifiés sur npm le 2026-10-13 et installés dans le projet de vérification :

PaquetVersionCompatibilitéExports utiles
@casl/ability7.0.1 (2026-07-06)sans dépendance AngularAbilityBuilder, createMongoAbility, MongoAbility, Ability
@casl/angular10.0.3 (2026-08-08)@angular/core 16 à ^22.0.0, @casl/ability ^7AbilityServiceSignal, AbilityService, AblePipe : ce sont les trois seuls exports, il n'y a pas de directive

Les règles s'écrivent avec AbilityBuilder, à partir de la session. manage et all sont deux mots réservés de CASL : toutes les actions, sur tous les sujets.

src/app/auth/ability.ts
import { AbilityBuilder, createMongoAbility, MongoAbility } from '@casl/ability';
import { Action, Session, Subject } from './session';

// le type des capacités de l'application : [action, sujet]
export type AppAbility = MongoAbility<[Action | 'manage', Subject | 'all']>;

// les règles, définies UNE fois, à partir des rôles renvoyés par /auth/me
export function rulesFor(session: Session | null) {
  const { can, rules } = new AbilityBuilder<AppAbility>(createMongoAbility);
  if (session?.roles.includes('admin')) {
    can('manage', 'all'); // 'manage' + 'all' : tous les droits
  } else if (session?.roles.includes('customer')) {
    can('read', 'Product');
  }
  return rules;
}

L'instance CASL est fournie une fois pour toute l'application, et le service d'authentification la met à jour à chaque changement de session. Le jeton d'injection est la classe Ability : dans la version 7, c'est elle que lit @casl/angular (le code compilé de AbilityServiceSignal fait inject(Ability)).

src/app/app.config.ts
// l'instance CASL que lit AbilityServiceSignal (le jeton d'injection est la classe Ability)
{ provide: Ability, useValue: createMongoAbility() },

Dans AuthService, cette instance est injectée par la même classe, et chaque changement de session lui passe les nouvelles règles.

src/app/auth/auth.service.ts
private readonly ability = inject(Ability);
// ...
private setSession(session: Session | null): void {
  this._session.set(session);
  this.ability.update(rulesFor(session)); // CASL : mêmes règles, recalculées à chaque changement de session
}

Dans un composant, AbilityServiceSignal expose une fonction can qui lit un signal interne, mis à jour à chaque update() des règles : le template réagit comme avec un signal ordinaire.

src/app/pages/home.ts
export class Home {
  protected readonly auth = inject(AuthService);
  private readonly http = inject(HttpClient);
  private readonly abilityService = inject<AbilityServiceSignal<AppAbility>>(AbilityServiceSignal);
  protected readonly can = this.abilityService.can;

Le template l'utilise avec @if (can('delete', 'Product')), déjà visible plus haut. Le paquet installé appelle deux remarques. Le README de @casl/angular qualifie les pipes de deprecated et recommande AbilityServiceSignal. Et l'import du pipe AblePipe dans un composant standalone échoue à la compilation, avec NG2012: Component imports must be standalone components, directives, pipes, or must be NgModules : ses types publiés ne portent pas les métadonnées Angular. On s'en tient donc à AbilityServiceSignal.

Et ngx-permissions ?

On trouve souvent ngx-permissions dans les projets existants. Sa dernière version, 19.0.0, date du 2025-02-04 : aucune publication pour Angular 20, 21 ou 22. Sa plage déclarée, >=13 || >25, est ouverte et ne bloque pas l'installation, mais elle ne garantit rien : la bibliothèque n'a pas été publiée pour ces versions. À éviter pour un nouveau projet ; dans un projet v20 qui l'utilise, c'est un bon candidat au remplacement par @if (auth.can(...)) ou CASL.

Le serveur applique les mêmes règles

Tout ce qui précède décide de ce qu'on affiche. Le serveur, lui, décide de ce qui est permis, avec la même règle écrite de son côté. C'est ce middleware qui a répondu 403 à la requête forcée d'alice en section 1.

api/server.cjs
// le serveur applique LUI-MÊME les règles : session obligatoire, écriture réservée au rôle admin
server.use('/api', (req, res, next) => {
  if (!req.session) return res.status(401).json({ error: 'Non authentifié' });
  if (req.method !== 'GET' && !req.session.roles.includes('admin')) {
    return res.status(403).json({ error: 'Réservé au rôle admin' });
  }
  next();
}, checkXsrf, router);

Avec CASL, la même définition de règles peut être partagée entre un back-end Node et Angular (@casl/ability ne dépend pas d'Angular) ; avec un back-end Java ou .NET, il faut écrire la règle deux fois, et garder la version serveur comme référence.

À retenir Les rôles viennent de /auth/me. Les composants demandent une permission (can('delete', 'Product')), pas un rôle. Dans le template, @if (auth.can(...)) plutôt qu'une directive. Quand les règles grossissent : CASL 7 + @casl/angular 10 avec AbilityServiceSignal. ngx-permissions n'a rien publié depuis Angular 19. Et le serveur vérifie toujours.
