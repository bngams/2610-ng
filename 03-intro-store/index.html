Angular 22 — Un service comme store

Dès que deux composants éloignés affichent la même donnée, il faut un endroit unique qui la garde : un store. En Angular 22, un service et quelques signals suffisent pour en écrire un propre. Cette page construit ce pattern sur deux exemples, le panier et la session, traite l'asynchrone, puis montre quand passer à NgRx SignalStore. Chaque extrait de code est copié d'un projet Angular 22 qui compile (ng build), dont les tests passent (ng test, 16 tests verts) et dont le comportement décrit ici a été vérifié dans le navigateur ; ce projet de vérification n'est pas livré.

Imprimable : Ctrl/Cmd + P puis « Enregistrer en PDF ». Avant cette page, la synthèse du jour 1 (signals, computed, effect) et la démo HTTP. Pages voisines du jour 3 : l'authentification et le workspace multi-projets. Pour pratiquer, suivez le lab MiniShop.

Le fil rouge est une petite boutique : un catalogue, un panier, un utilisateur connecté. Dans le projet de vérification, un faux back-end (un intercepteur HTTP) répondait aux URL /api/... et /auth/... ; il n'apparaît pas dans les extraits.

1Pourquoi un store

Prenons le panier. Trois composants en ont besoin, et ils ne sont pas parents les uns des autres : le badge du header affiche le nombre d'articles, la page panier liste les lignes et permet de changer les quantités, la page de commande lit le total puis vide le panier. Faire remonter et redescendre ces données avec des input() et des output() à travers toute l'arborescence serait fragile ; garder une copie dans chaque composant serait pire, car les copies finiraient par diverger.

Un store répond à trois questions à la fois :

QuestionRéponse du store
Où est la donnée ?À un seul endroit : c'est la source unique de vérité. Tout le monde lit la même valeur.
Qui a le droit de la modifier ?Le store seul. Les composants demandent une modification en appelant une méthode, ils n'écrivent jamais l'état eux-mêmes.
Comment les lecteurs sont-ils prévenus ?Par les signals : quand l'état change, tout ce qui le lit (template, computed) se met à jour.

Le schéma suivant montre ces règles sur le panier. Les flèches bleues sont des lectures, les flèches orange des appels de méthode ; la flèche barrée est ce qu'un composant n'a pas le droit de faire.

À retenir Un store, c'est une donnée partagée à un seul endroit, qui seul a le droit de la modifier, et qui prévient ses lecteurs. Les composants lisent et demandent ; le store décide et écrit.

2Le pattern « service + signals »

Le pattern tient en cinq pièces, toutes déjà vues au jour 1. Le tableau les présente avant l'extrait, qui les montre dans l'ordre sur le panier.

PièceÉcritureRôle
Le service, unique@Injectable({ providedIn: 'root' })une seule instance pour toute l'application, partagée par tous ceux qui l'injectent
L'étatprivate readonly _lines = signal(...)un WritableSignal privé : seul le store peut appeler set ou update
La vue publiquereadonly lines = this._lines.asReadonly()le même signal, sans set ni update : les composants lisent, c'est tout
Les sélecteurscomputed(() => ...)les valeurs dérivées (nombre d'articles, total), recalculées seulement quand l'état change
Les actionsdes méthodes : add(), remove()...les seules portes d'entrée pour modifier l'état, avec une mise à jour immuable (la fonction passée à update renvoie un nouveau tableau)

Voici le début du store du panier, qui pose ces pièces. L'état initial vient de readSavedCart(), qui relit le panier sauvegardé ; cette fonction, les actions et le constructeur avec son effect sont détaillés à la section 3.

src/app/cart/cart.store.ts
import { computed, effect, Injectable, signal } from '@angular/core';
import { CartLine, Product } from './cart.model';

const STORAGE_KEY = 'minishop.cart';

@Injectable({ providedIn: 'root' }) // UNE instance pour toute l'application
export class CartStore {
  // l'état : PRIVÉ, seul le store peut l'écrire
  private readonly _lines = signal<CartLine[]>(readSavedCart());

  // la vue publique : un Signal en lecture seule (pas de set / update)
  readonly lines = this._lines.asReadonly();

  // les sélecteurs : des computed, dérivés de l'état, jamais stockés
  readonly count = computed(() => this._lines().reduce((n, line) => n + line.qty, 0));
  readonly total = computed(() =>
    this._lines().reduce((sum, line) => sum + line.qty * line.product.price, 0),
  );
  readonly isEmpty = computed(() => this._lines().length === 0);

Et @Service() ?

Angular 22.0 ajoute un décorateur @Service(), pensé pour ce cas : un service fourni automatiquement à la racine. Il n'a pas d'option providedIn ; ses seules options sont autoProvided (mettre false pour le fournir soi-même dans une liste de providers) et factory. Le projet de vérification l'a exercé dans un test, qui vérifie que deux inject renvoient la même instance.

src/app/pitfalls/pitfalls.spec.ts
@Service() // Angular 22 : fourni à la racine par défaut, pas d'option providedIn
class Counter {
  readonly value = signal(0);
}
  // ...
  it('@Service() est un singleton racine', () => {
    expect(TestBed.inject(Counter)).toBe(TestBed.inject(Counter));
  });

Les deux écritures sont valides en v22. Cette page garde @Injectable({ providedIn: 'root' }), que vous retrouverez dans tout le code existant, y compris vos projets v20 où @Service() n'existe pas.

Pas d'effect pour une valeur dérivée

Une valeur qui se calcule à partir de l'état (le nombre d'articles, le total, « est-ce un admin ? ») est un computed. On voit parfois la même chose écrite avec un second signal et un effect qui le recopie : c'est un état dupliqué, recalculé en retard, et une source de bugs. effect sert aux effets de bord vers l'extérieur du monde des signals : écrire dans localStorage, journaliser, piloter une API du navigateur.

Trois pièges, réunis dans un store à ne pas écrire

Pour voir les pièges en vrai, le projet de vérification contient un BadCartStore qui les cumule. Il compile sans erreur, ce qui est justement le problème : rien ne vous avertit.

src/app/pitfalls/bad-cart.store.ts
// À NE PAS FAIRE : les trois pièges classiques, réunis dans un seul store
@Injectable({ providedIn: 'root' })
export class BadCartStore {
  readonly lines = signal<CartLine[]>([]); // piège 1 : WritableSignal public, tout le monde peut écrire
  readonly count = signal(0); // piège 2 : état dupliqué, recopié à la main

  constructor() {
    // piège 2 (suite) : un effect pour DÉRIVER une valeur, au lieu d'un computed
    effect(() => this.count.set(this.lines().reduce((n, line) => n + line.qty, 0)));
  }

  add(product: Product) {
    this.lines().push({ product, qty: 1 }); // piège 3 : mutation EN PLACE, personne n'est prévenu
  }
}

Le test suivant montre l'effet combiné. L'application tourne (l'effect a déjà calculé count = 0), puis on ajoute un article par la méthode du store : la ligne est bien dans le tableau, mais count reste à 0, et n'importe qui peut ensuite vider le panier de l'extérieur.

src/app/pitfalls/pitfalls.spec.ts
it('BadCartStore : count reste à 0 après add(), et on écrit l\'état de dehors', () => {
  const bad = TestBed.inject(BadCartStore);
  TestBed.tick(); // l'application tourne : l'effect a déjà calculé count = 0
  bad.add({ id: 1, name: 'Stylo', price: 1.5 });
  TestBed.tick();
  expect(bad.lines()).toHaveLength(1); // la ligne est bien là...
  expect(bad.count()).toBe(0); // ...mais personne n'a été prévenu
  bad.lines.set([]); // et n'importe quel composant peut tout effacer
  expect(bad.lines()).toHaveLength(0);
});

Le piège 3 tient à la façon dont un signal décide de prévenir ses lecteurs : il compare l'ancienne et la nouvelle valeur avec Object.is. Un tableau modifié en place reste le même tableau, donc même un set() explicite ne prévient personne ; seul un nouveau tableau le fait. Un second test isole ce mécanisme sur un signal nu.

src/app/pitfalls/pitfalls.spec.ts
it('muter le tableau en place ne prévient personne', () => {
  const lines = signal<number[]>([1]);
  const count = computed(() => lines().length);
  expect(count()).toBe(1);
  lines().push(2); // mutation EN PLACE : même référence
  lines.set(lines()); // set() du MÊME tableau : Object.is(ancien, nouveau), pas de notification
  expect(count()).toBe(1); // le computed n'a rien vu
  lines.update((l) => [...l, 3]); // nouveau tableau => notification
  expect(count()).toBe(3);
});

Un détail découvert en écrivant le test : si l'effect du BadCartStore n'a pas encore tourné au moment du push, sa première exécution lit le tableau déjà modifié et count paraît juste. Le bug dépend donc du moment où l'on regarde, ce qui le rend encore plus difficile à trouver.

Le tableau résume les trois pièges, dans l'ordre des commentaires du BadCartStore, avec leur correctif.

PiègeSymptômeCorrectif
Exposer le WritableSignalun composant fait lines.set([]) et le panier se vide sans passer par le storesignal private + vue asReadonly()
Dupliquer l'état (count en signal à part, recopié par un effect)valeurs en retard ou fausses, ordre d'exécution qui compteun computed dérivé de l'état unique

3Exemple 1 : le panier

La section 2 a posé l'état, la vue publique et les sélecteurs du CartStore. Il reste à écrire les actions, à brancher les composants, puis à faire survivre le panier à un rechargement de la page.

Les actions : add, changeQty, remove, clear

Chaque action passe par update, qui reçoit l'état courant et doit renvoyer le nouvel état. On ne modifie jamais une ligne existante : map produit un nouveau tableau dans lequel seule la ligne concernée est remplacée par une copie ({ ...line, qty }), filter en produit un sans la ligne retirée. Une quantité tombée à 0 retire la ligne, pour que changeQty reste la seule action dont la page a besoin pour les boutons « + » et « - ».

src/app/cart/cart.store.ts
// les actions : des méthodes, qui produisent un NOUVEAU tableau
add(product: Product) {
  this._lines.update((lines) => {
    const existing = lines.find((line) => line.product.id === product.id);
    return existing
      ? lines.map((line) => (line === existing ? { ...line, qty: line.qty + 1 } : line))
      : [...lines, { product, qty: 1 }];
  });
}

changeQty(productId: number, qty: number) {
  if (qty <= 0) {
    this.remove(productId);
    return;
  }
  this._lines.update((lines) =>
    lines.map((line) => (line.product.id === productId ? { ...line, qty } : line)),
  );
}

remove(productId: number) {
  this._lines.update((lines) => lines.filter((line) => line.product.id !== productId));
}

clear() {
  this._lines.set([]);
}

Persister dans localStorage avec un effect

Pour que le panier survive à un F5, deux gestes suffisent. Au démarrage, l'état initial est relu depuis localStorage : c'est la fonction readSavedCart(), passée à signal() dans l'extrait de la section 2. Ensuite, un effect déclaré dans le constructeur de la classe (placé avant les actions dans le fichier) recopie l'état à chaque changement. C'est bien un effet de bord vers l'extérieur des signals, le cas d'usage légitime d'effect.

src/app/cart/cart.store.ts
constructor() {
  // effet de bord : recopier l'état dans localStorage à chaque changement
  effect(() => localStorage.setItem(STORAGE_KEY, JSON.stringify(this._lines())));
}

La relecture est entourée d'un try/catch, car elle peut échouer pour des raisons qui ne dépendent pas de vous : un JSON corrompu, un stockage désactivé. Un panier vide vaut mieux qu'une application qui ne démarre pas.

src/app/cart/cart.store.ts
// relire le panier sauvegardé, sans jamais faire planter le démarrage
function readSavedCart(): CartLine[] {
  try {
    const saved = localStorage.getItem(STORAGE_KEY);
    return saved ? (JSON.parse(saved) as CartLine[]) : [];
  } catch {
    return []; // JSON corrompu, ou stockage indisponible refusé par le navigateur
  }
}

Voici ce que montre le navigateur, en partant d'un localStorage vide.

ActionObservé
« Ajouter » deux fois sur Stylo, une fois sur Cahier, depuis le cataloguele badge passe à Panier (3) ; localStorage['minishop.cart'] contient les deux lignes (Stylo × 2, Cahier × 1)

Le symbole €7.00 vient de la locale par défaut (en-US) du pipe currency ; pour un affichage français (7,00 €), on enregistre les données de la locale avec registerLocaleData et on fournit LOCALE_ID (non exercé ici).

Bon pour un panier, pas pour un jeton d'authentification

localStorage est lisible par tout le JavaScript de la page, y compris un script injecté par une faille XSS. Pour un panier, ce n'est pas grave : il ne contient rien de secret, et le pire est qu'on le lise. Pour un jeton d'authentification, c'est grave : un script qui le lit peut l'envoyer ailleurs et se faire passer pour l'utilisateur. Un jeton vit plutôt dans un cookie HttpOnly, que le JavaScript ne peut pas lire ; c'est le sujet de la page authentification.

Une seconde conséquence est moins évidente : ce que l'on relit de localStorage peut avoir été modifié par l'utilisateur, prix compris (onglet Application des DevTools). Le panier côté client sert à l'affichage ; au moment de la commande, le serveur recalcule les prix à partir des identifiants et des quantités.

À retenir Des actions qui renvoient toujours un nouveau tableau ; des composants qui injectent le store, lisent ses sélecteurs et appellent ses méthodes. La persistance tient en deux gestes : relire à la construction (avec try/catch), recopier avec un effect. localStorage convient à un panier, jamais à un jeton.

4Exemple 2 : la session

Le second store garde l'utilisateur connecté. Le header affiche son nom, un menu se montre aux seuls administrateurs, un guard protège des routes : autant de lecteurs éloignés d'une même donnée. La différence avec le panier est que l'état vient du serveur : il faut le charger, et pendant ce temps, l'application doit savoir qu'elle ne sait pas encore.

L'état et les sélecteurs

L'état regroupe l'utilisateur, un indicateur de chargement et un message d'erreur, dans un seul signal privé. Les sélecteurs en dérivent ce dont les composants ont besoin : isLoggedIn, roles, et même un isAdmin construit sur un autre computed. L'état étant un objet, on n'expose pas le signal entier avec asReadonly() : un computed par champ utile joue le même rôle de lecture seule, et cache la forme interne de l'état.

src/app/session/session.store.ts
export interface User {
  id: number;
  name: string;
  roles: string[];
}

interface SessionState {
  user: User | null;
  loading: boolean;
  error: string | null;
}

@Injectable({ providedIn: 'root' }) // la session DOIT être unique dans l'application
export class SessionStore {
  private readonly http = inject(HttpClient);
  private readonly state = signal<SessionState>({ user: null, loading: false, error: null });

  // sélecteurs
  readonly user = computed(() => this.state().user);
  readonly isLoggedIn = computed(() => this.state().user !== null);
  readonly roles = computed(() => this.state().user?.roles ?? []);
  readonly isAdmin = computed(() => this.roles().includes('admin'));
  readonly loading = computed(() => this.state().loading);
  readonly error = computed(() => this.state().error);

Les actions appellent HTTP

loadMe() demande au serveur « qui suis-je ? » avec GET /auth/me. Avec une session par cookie, le navigateur joint le cookie tout seul ; le store n'a aucun jeton à manipuler. Un 401 n'est pas une panne : il veut dire « personne n'est connecté », d'où user: null sans message d'erreur ; toute autre erreur affiche « Session indisponible ». login suit le même schéma : noter le chargement, appeler, ranger le résultat avec un patch privé qui fusionne l'état. logout se contente de vider user une fois le serveur d'accord.

src/app/session/session.store.ts
  // au démarrage : « qui suis-je ? » ; le cookie de session part avec la requête
  loadMe() {
    this.patch({ loading: true, error: null });
    this.http.get<User>('/auth/me').subscribe({
      next: (user) => this.patch({ user, loading: false }),
      error: (err: HttpErrorResponse) =>
        this.patch({
          user: null,
          loading: false,
          // 401 = personne n'est connecté, ce n'est pas une panne
          error: err.status === 401 ? null : 'Session indisponible',
        }),
    });
  }

  login(email: string, password: string) {
    this.patch({ loading: true, error: null });
    this.http.post<User>('/auth/login', { email, password }).subscribe({
      next: (user) => this.patch({ user, loading: false }),
      error: () => this.patch({ loading: false, error: 'Identifiants refusés' }),
    });
  }

  logout() {
    this.http.post('/auth/logout', {}).subscribe({
      next: () => this.patch({ user: null }),
    });
  }

  private patch(partial: Partial<SessionState>) {
    this.state.update((s) => ({ ...s, ...partial }));
  }
}

La session est chargée une fois, au démarrage de l'application, par un initialiseur déclaré dans app.config.ts.

src/app/app.config.ts
// au démarrage, la session demande « qui suis-je ? »
provideAppInitializer(() => inject(SessionStore).loadMe()),

Telle qu'écrite, loadMe() ne renvoie rien : l'application démarre sans attendre la réponse, et affiche « … » le temps du chargement. Pour la faire attendre, l'initialiseur peut renvoyer une Promise ou un Observable ; cette variante n'a pas été exercée ici. Un guard, lui, doit tenir compte de loading() avant de conclure qu'il n'y a personne ; la page authentification revient sur ce point.

Le widget du header n'a plus qu'à lire les sélecteurs. Les trois états (chargement, connecté, anonyme) se lisent dans le @if.

src/app/session/session-status.ts

Vérifié dans le navigateur : « Se connecter (démo) » affiche Camille (customer, admin) et « Se déconnecter » ; après F5, le header montre « … » puis de nouveau Camille (customer, admin), car loadMe() a interrogé /auth/me et le faux serveur a reconnu sa session.

Une seule session par application

Le panier et la session doivent être des singletons. Avec deux instances de SessionStore, le header dirait « connecté » pendant qu'une page dirait « anonyme ». providedIn: 'root' garantit une instance par application ; le piège classique est de réécrire providers: [SessionStore] dans un composant, ce qui crée une seconde instance, vide, pour ce composant et ses enfants. Le test suivant reproduit ce que fait un providers de composant : un injecteur enfant qui déclare de nouveau le service, et qui en fabrique donc une autre instance ; session est le store injecté dans le beforeEach du fichier.

src/app/session/session.store.spec.ts
it('un providers: [SessionStore] local crée une DEUXIÈME session', () => {
  const local = Injector.create({ providers: [SessionStore], parent: TestBed.inject(Injector) });
  expect(local.get(SessionStore)).not.toBe(session);
});

Le problème change d'échelle avec les micro-frontends : chaque application chargée à part a son propre injecteur racine, donc sa propre session. Partager le code de la bibliothèque (singleton: true dans la configuration de Module Federation) ne suffit pas : chaque bootstrapApplication crée encore sa propre instance. Il faut partager l'instance, par exemple avec providedIn: 'platform' sur une plateforme commune. Ces montages n'ont pas été exercés sur cette page ; ils sont traités dans la page workspace multi-projets.

À retenir Le même pattern, avec un état venu du serveur : user, loading et error dans un seul signal privé, isLoggedIn et roles en computed, des actions qui appellent HTTP. Un 401 sur /auth/me veut dire « anonyme ». Une session est un singleton : jamais de providers: [SessionStore] local.

5L'asynchrone dans un store

Les deux stores précédents appellent déjà HTTP. Cette section met des mots sur le schéma suivi, puis montre deux cas plus délicats : une mise à jour optimiste, et une action déclenchée à chaque frappe.

Le schéma de base : subscribe, puis update

Une action asynchrone suit trois temps : marquer le chargement, appeler, ranger le résultat ou l'erreur. Le catalogue le fait sur GET /api/products. Le subscribe est dans le store, pas dans le composant : le composant appelle load() et lit products(), loading(), error().

src/app/catalog/products.store.ts
// action asynchrone : on note le chargement, on appelle, on range le résultat
load() {
  this.patch({ loading: true, error: null });
  this.http.get<Product[]>('/api/products').subscribe({
    next: (products) => this.patch({ products, loading: false }),
    error: () => this.patch({ loading: false, error: 'Catalogue indisponible' }),
  });
}

Ce schéma convient aux actions ponctuelles : charger une liste, se connecter, enregistrer. Un HttpClient émet une fois puis se termine, il n'y a rien à désabonner.

Mise à jour optimiste, et rollback

Mettre un produit en favori ne doit pas attendre le serveur : l'étoile se remplit tout de suite (mise à jour optimiste), la requête part, et si le serveur refuse, on remet l'ancienne valeur (rollback) et on affiche une erreur.

src/app/catalog/products.store.ts
// mise à jour optimiste : l'écran change tout de suite, le serveur confirme ensuite
toggleFavorite(id: number) {
  const wanted = !this.state().products.find((p) => p.id === id)?.favorite;
  this.setFavorite(id, wanted); // 1. optimiste
  this.http.put(`/api/products/${id}/favorite`, { favorite: wanted }).subscribe({
    error: () => {
      this.setFavorite(id, !wanted); // 2. rollback : on remet l'ancienne valeur
      this.patch({ error: 'Favori non enregistré' });
    },
  });
}

private setFavorite(id: number, favorite: boolean) {
  this.state.update((s) => ({
    ...s,
    products: s.products.map((p) => (p.id === id ? { ...p, favorite } : p)),
  }));
}

Le rollback inverse la valeur d'un produit plutôt que de restaurer une copie de toute la liste : si un autre changement est arrivé entre-temps, il n'est pas écrasé. Le test vérifie les deux temps, avant et après la réponse ; store et http sont préparés dans un beforeEach, montré à la section 7.

src/app/catalog/products.store.spec.ts
it('favori optimiste, puis rollback si le serveur refuse', () => {
  store.toggleFavorite(3);
  expect(store.products()[0].favorite).toBe(true); // tout de suite, avant la réponse
  http.expectOne('/api/products/3/favorite').flush(null, { status: 500, statusText: 'KO' });
  expect(store.products()[0].favorite).toBe(false); // rollback : plus en favori
  expect(store.error()).toBe('Favori non enregistré');
});

Dans le navigateur, le faux serveur refuse le favori du Sac à dos et répond au bout de 300 ms. Lu 100 ms après le clic, donc avant la réponse, le bouton affiche déjà ★ ; une fois la réponse arrivée, il revient à ☆ et « Favori non enregistré » apparaît. Le favori du Stylo, accepté, reste à ★.

Une action à chaque frappe : il faut annuler

Une recherche déclenchée à chaque frappe est un flux, pas une action ponctuelle. Avec subscribe dans la méthode, les réponses peuvent arriver dans le désordre et la dernière affichée ne serait pas forcément la dernière demandée. Il faut un switchMap, qui annule la requête précédente, et souvent un debounceTime. Trois écritures s'offrent à vous :

ÉcriturePrincipeOù la voir
rxMethod (NgRx SignalStore)une méthode du store construite avec un pipe RxJS ; elle accepte une valeur, un signal ou un Observablesection 6, exercée dans le projet de vérification
Un Subject dans le servicela méthode fait next(q) ; le constructeur branche switchMap et takeUntilDestroyed()même logique que rxMethod, écrite à la main
httpResourcela requête se recalcule quand le signal de recherche change, et annule la précédentedémo HTTP du jour 2
À retenir Une action asynchrone : marquer le chargement, appeler, ranger le résultat ou l'erreur, avec le subscribe dans le store. Une mise à jour optimiste modifie d'abord, puis annule précisément si le serveur refuse. Pour un flux (recherche à la frappe), il faut switchMap : rxMethod, un Subject, ou httpResource.

📖 HttpClient · interop RxJS · switchMap

6Quand passer à NgRx SignalStore

Après deux ou trois stores écrits à la main, des morceaux se répètent : le patch privé, le trio loading / error / données, la méthode à base de switchMap. NgRx SignalStore (@ngrx/signals) standardise exactement ce pattern, avec les mêmes signals dessous. La version vérifiée sur npm le 13 octobre 2026 est la 22.0.1, qui demande @angular/core ^22.0.0 ; elle s'installe avec npm install @ngrx/signals@22.

Chaque pièce du pattern de la section 2 a son équivalent. Le tableau sert de clé de lecture pour l'extrait qui suit.

Service + signalsSignalStore
@Injectable({ providedIn: 'root' })signalStore({ providedIn: 'root' }, ...)
private _lines = signal(...) + asReadonly()withState({ lines: [] }) : l'état est protégé par défaut, en lecture seule hors du store
computed(...)withComputed(({ lines }) => ({ count: computed(...) }))
méthodes avec this._lines.update(...)withMethods((store) => ({ add() { patchState(store, ...) } }))

Voici le même panier, réduit à trois actions et sans la persistance. patchState accepte soit un objet partiel ({ lines: [] }), soit une fonction qui reçoit l'état et renvoie la partie à remplacer : l'immuabilité reste votre responsabilité, comme avec update.

src/app/ngrx/cart.signal-store.ts
import { computed } from '@angular/core';
import { patchState, signalStore, withComputed, withMethods, withState } from '@ngrx/signals';
import { CartLine, Product } from '../cart/cart.model';

type CartState = { lines: CartLine[] };

// le MÊME panier, écrit avec NgRx SignalStore
export const CartSignalStore = signalStore(
  { providedIn: 'root' },
  withState<CartState>({ lines: [] }), // l'état : protégé, en lecture seule hors du store
  withComputed(({ lines }) => ({
    // les sélecteurs
    count: computed(() => lines().reduce((n, line) => n + line.qty, 0)),
    total: computed(() => lines().reduce((sum, line) => sum + line.qty * line.product.price, 0)),
  })),
  withMethods((store) => ({
    // les actions : patchState applique une mise à jour partielle et immuable
    add(product: Product) {
      patchState(store, ({ lines }) => {
        const existing = lines.find((line) => line.product.id === product.id);
        return {
          lines: existing
            ? lines.map((line) => (line === existing ? { ...line, qty: line.qty + 1 } : line))
            : [...lines, { product, qty: 1 }],
        };
      });
    },
    remove(productId: number) {
      patchState(store, ({ lines }) => ({
        lines: lines.filter((line) => line.product.id !== productId),
      }));
    },
    clear() {
      patchState(store, { lines: [] });
    },
  })),
);

Le store s'injecte comme un service, inject(CartSignalStore), et s'utilise de la même façon : cart.count(), cart.add(p). La protection de l'état est vérifiée par le compilateur : appeler patchState depuis l'extérieur ne compile pas, ce que confirme ce test (sans le commentaire @ts-expect-error, tsc signale une erreur).

src/app/ngrx/cart.signal-store.spec.ts
it("l'état est protégé : patchState refusé hors du store", () => {
  const cart = TestBed.inject(CartSignalStore);
  // @ts-expect-error : protectedState par défaut, le store n'est pas un WritableStateSource
  patchState(cart, { lines: [] });
});

rxMethod pour les flux

Le cas de la recherche à la frappe, laissé ouvert à la section 5, a une réponse toute faite : rxMethod, importé de @ngrx/signals/rxjs-interop. On lui donne un pipe RxJS ; le catchError reste dans le switchMap, sinon la première erreur terminerait le flux et la recherche ne répondrait plus.

src/app/ngrx/catalog.signal-store.ts
import { rxMethod } from '@ngrx/signals/rxjs-interop';
import { catchError, debounceTime, distinctUntilChanged, of, pipe, switchMap, tap } from 'rxjs';
// ...
export const CatalogSignalStore = signalStore(
  { providedIn: 'root' },
  withState({ products: [] as Product[], loading: false }),
  withMethods((store, http = inject(HttpClient)) => ({
    // rxMethod : une méthode qui accepte une valeur, un signal ou un Observable
    search: rxMethod<string>(
      pipe(
        debounceTime(300),
        distinctUntilChanged(),
        tap(() => patchState(store, { loading: true })),
        switchMap((q) =>
          http.get<Product[]>('/api/products', { params: { q } }).pipe(
            catchError(() => of([] as Product[])), // l'erreur reste DANS le switchMap
          ),
        ),
        tap((products) => patchState(store, { products, loading: false })),
      ),
    ),
  })),
);

Un composant peut passer à search une valeur, ou un signal : rxMethod suit alors ce signal et relance la recherche à chaque changement, sans abonnement à gérer. L'appel se fait dans le constructeur (un contexte d'injection), pour que ce suivi s'arrête avec le composant. Dans ngOnInit, le suivi serait rattaché à l'injecteur racine du store et ne s'arrêterait jamais . Essayé dans le projet de vérification, l'appel depuis ngOnInit affiche en développement un avertissement de @ngrx/signals 22 : l'usage est déprécié et lèvera une erreur dans une version future ; depuis le constructeur, la console reste vide.

src/app/ngrx/signal-store-page.ts
constructor() {
  // dans le constructeur (contexte d'injection) : le suivi s'arrête avec le composant
  this.catalog.search(this.query); // rxMethod suit le signal : chaque frappe relance la recherche
}

Pour une collection d'objets identifiés (des produits, des commandes), withEntities<Product>() de @ngrx/signals/entities ajoute entities, ids et entityMap, avec des fonctions toutes prêtes à passer à patchState : addEntity, setAllEntities, updateEntity, removeEntity… (noms lus dans les types installés, non exercés ici).

Et votre code NgRx « classique » ?

Vos projets v20 utilisent NgRx Store avec actions, reducers, effects et selectors. Rien n'oblige à les réécrire : depuis un composant, store.selectSignal(selecteur) lit un sélecteur existant sous forme de signal, et se combine avec des computed. Le projet de vérification a installé @ngrx/store 22.0.1 avec un petit reducer à l'ancienne ; la page affiche bien « NgRx classique, lu en signal : 2 ».

src/app/ngrx/signal-store-page.ts
// code NgRx « classique » existant (v20) : selectSignal le lit comme un signal
private readonly store = inject(Store);
protected readonly legacyCount = this.store.selectSignal(selectLegacyCount);

Pour une équipe attachée au style actions / reducers, @ngrx/signals/events exporte aussi event, withReducer et withEventHandlers : un pont entre les deux mondes, non exercé sur cette page.

7Tester un store

Un store se teste sans afficher le moindre composant : c'est un de ses grands avantages. Dans un projet créé avec Angular 22, ng test lance Vitest (le builder @angular/build:unit-test) ; un projet mis à jour depuis la v20 garde Karma tant qu'on ne le migre pas. Le test tient en trois gestes : obtenir le store avec TestBed.inject, appeler des actions, vérifier les sélecteurs.

src/app/cart/cart.store.spec.ts
import { TestBed } from '@angular/core/testing';
import { CartStore } from './cart.store';
// ...
const PEN = { id: 1, name: 'Stylo', price: 1.5 };
const NOTEBOOK = { id: 2, name: 'Cahier', price: 4 };
// ...
describe('CartStore', () => {
  beforeEach(() => localStorage.clear());
  // ...
  it('calcule count et total après des actions', () => {
    const cart = TestBed.inject(CartStore);
    cart.add(PEN);
    cart.add(PEN);
    cart.add(NOTEBOOK);
    expect(cart.count()).toBe(3);
    expect(cart.total()).toBe(7); // 2 x 1,5 + 4
  });

Aucun configureTestingModule n'est nécessaire : le store est providedIn: 'root', TestBed sait le fabriquer. Chaque test repart d'un TestBed neuf, donc d'une instance neuve ; comme le store relit localStorage à sa construction, le beforeEach vide aussi le stockage.

La persistance se teste aussi. Deux outils de TestBed servent ici : TestBed.tick() exécute les effect en attente, et TestBed.resetTestingModule() jette l'injecteur, ce qui revient à relancer l'application comme après un F5.

src/app/cart/cart.store.spec.ts
it('sauvegarde dans localStorage, et relit au démarrage', () => {
  TestBed.inject(CartStore).add(NOTEBOOK);
  TestBed.tick(); // laisse l'effect s'exécuter
  expect(JSON.parse(localStorage.getItem('minishop.cart')!)).toHaveLength(1);

  TestBed.resetTestingModule(); // une « nouvelle application », comme après F5
  expect(TestBed.inject(CartStore).count()).toBe(1);
});

Pour un store qui appelle HTTP, provideHttpClientTesting() remplace le réseau, et HttpTestingController permet de répondre à la main, au moment choisi : c'est ce qui a permis de vérifier l'état optimiste avant la réponse, à la section 5.

src/app/catalog/products.store.spec.ts
beforeEach(() => {
  TestBed.configureTestingModule({ providers: [provideHttpClient(), provideHttpClientTesting()] });
  store = TestBed.inject(ProductsStore);
  http = TestBed.inject(HttpTestingController);
  store.load();
  http.expectOne('/api/products').flush([{ id: 3, name: 'Sac à dos', price: 39 }]);
