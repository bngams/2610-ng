Angular 22 — Workspace, bibliothèques et micro-frontends

Quand une application grossit, on finit par la découper. Cette page présente trois niveaux de découpage : une application avec des routes lazy, un workspace qui contient plusieurs applications et des bibliothèques partagées, puis des micro-frontends assemblés dans le navigateur. Elle compare au passage le workspace du CLI Angular et Nx. Chaque commande, chaque sortie et chaque extrait de code vient d'une exécution réelle avec Angular CLI 22.2.2 et Node 24.18.0 (le workspace Nx de la section 4 a ses propres versions, indiquées là-bas) ; l'exemple Native Federation a été lancé et vérifié dans le navigateur. Les projets de vérification ne sont pas livrés.

Imprimable : Ctrl/Cmd + P puis « Enregistrer en PDF ». Les autres synthèses du jour 3 : authentification et gestion d'état. Pour pratiquer : le lab Minishop (en cours d'écriture).

Le fil rouge est une boutique : une vitrine publique (fo, front-office), un back-office marchand (bo) et des bibliothèques communes. Pour les micro-frontends, une application hôte (shell) charge un catalogue servi par une autre application (mfe1).

1Trois paliers de découpage

Découper une application, c'est décider de ce qu'on compile et de ce qu'on déploie ensemble. Il y a trois paliers, et chacun ajoute de l'indépendance en échange de complexité. Le schéma les met côte à côte : ce qui change de l'un à l'autre, c'est le nombre de déploiements et le moment où les morceaux se rejoignent.

Le tableau suivant résume ce que chaque palier apporte et ce qu'il coûte. La dernière ligne est la plus importante : on monte d'un palier pour une raison d'organisation, pas parce que le code est gros.

1. Une application2. Un workspace3. Des micro-frontends
Ce qu'on livreun seul dist/un dist/ par applicationun shell et des remotes, chacun sur son serveur
Quand les morceaux se rejoignentà la compilationà la compilation (chaque app embarque les libs qu'elle importe)à l'exécution, dans le navigateur
Partage de codedes dossiers features/, shared/des bibliothèques importées par un alias @shop/…des dépendances partagées négociées à l'exécution
Coûtfaiblemoyen : configuration, règles de dépendanceélevé : versions, pannes à l'exécution, cohérence de l'UX
Le bon critèreune équipe, un rythme de livraisonplusieurs produits (vitrine, back-office) qui partagent du codeplusieurs équipes qui doivent livrer sans se synchroniser

Une application de 300 composants maintenue par une seule équipe reste très bien au palier 1, avec une route lazy par feature. À l'inverse, deux équipes qui livrent l'une le catalogue chaque jour et l'autre le compte client chaque mois ont un vrai motif de passer au palier 3. C'est le cas de nombreux projets Angular en entreprise, souvent montés en Module Federation sur un workspace Nx.

À retenir Trois paliers : une application avec des routes lazy, un workspace (plusieurs applications et des bibliothèques, compilées et déployées séparément), des micro-frontends (un shell qui charge des remotes à l'exécution). On choisit selon les équipes et le rythme de déploiement, pas selon la taille du code.

2Le workspace Angular CLI

Un workspace est un dossier avec un seul angular.json, un seul package.json et un seul node_modules, qui déclare plusieurs projets : des applications et des bibliothèques. Toutes partagent donc les mêmes versions d'Angular, ce qui est à la fois un confort et une contrainte.

Créer un workspace vide

D'habitude, ng new crée un workspace et une application du même nom. L'option --no-create-application crée seulement le contenant, sans application.

npx @angular/cli@22.2.2 new shop --no-create-application --package-manager=npm --skip-git
cd shop

Le fichier angular.json obtenu ne déclare encore aucun projet. La clé newProjectRoot indique où le CLI rangerait les projets par défaut, dans projects/.

shop/angular.json (juste après ng new)
{
  "$schema": "./node_modules/@angular/cli/lib/config/schema.json",
  "version": 1,
  "cli": {
    "packageManager": "npm"
  },
  "newProjectRoot": "projects",
  "projects": {
  }
}

Générer les applications dans apps/

Plutôt que de tout mettre à plat dans projects/, on range les applications dans apps/ et les bibliothèques dans libs/, une convention venue de Nx. C'est l'option --project-root qui choisit le dossier ; le nom du projet, lui, reste court (fo), car c'est lui qu'on tape ensuite dans ng serve fo. Les autres options évitent les questions interactives : un fichier de routes (--routing), du CSS simple, pas de rendu serveur (--ssr=false), pas de fichiers de test (--skip-tests).

npx ng generate application fo --project-root apps/fo --routing --style=css --ssr=false --skip-tests
npx ng generate application bo --project-root apps/bo --routing --style=css --ssr=false --skip-tests

La première commande affiche les fichiers créés, puis met à jour les trois fichiers communs du workspace.

Générer une bibliothèque, et ce que le CLI ajoute au tsconfig

Une bibliothèque se génère de la même façon. Elle a son propre package.json (son nom de paquet), un ng-package.json (pour ng-packagr, l'outil qui la compile) et un fichier public-api.ts, sa façade : seul ce qui y est exporté est visible des applications.

npx ng generate library models --project-root libs/models

La sortie, raccourcie, montre ces trois fichiers, le composant d'exemple models.ts et les mises à jour du workspace.

CREATE libs/models/ng-package.json (155 bytes)
CREATE libs/models/package.json (210 bytes)
...
CREATE libs/models/src/public-api.ts (70 bytes)
CREATE libs/models/src/lib/models.spec.ts (532 bytes)
CREATE libs/models/src/lib/models.ts (195 bytes)
UPDATE angular.json (5501 bytes)
UPDATE package.json (809 bytes)
UPDATE tsconfig.json (1118 bytes)

La ligne UPDATE tsconfig.json est la plus intéressante : le CLI y ajoute un alias qui pointe vers le dossier de sortie de la bibliothèque compilée.

shop/tsconfig.json (ajouté par ng generate library)
"paths": {
  "models": ["./dist/models"]
},

Un nom scopé : @shop/models

Importer from 'models' marche, mais ce nom nu ressemble à un paquet npm public. L'usage est de le préfixer par un scope, le nom de l'organisation : @shop/models. Ce nom est écrit à deux endroits, qu'il faut modifier ensemble.

FichierRôleValeur
libs/models/package.json, champ namele nom du paquet produit par ng build models"name": "@shop/models"
tsconfig.json, champ pathsl'alias que TypeScript résout dans le workspace"@shop/models": ["./dist/models"]

Pour models, on fait donc les deux modifications à la main : "name": "models" devient "name": "@shop/models" dans libs/models/package.json, et la clé "models" devient "@shop/models" dans les paths du tsconfig.

Plus simple : donner directement un nom scopé au générateur. Le CLI remplit alors les deux endroits d'un coup, et le projet s'appelle @shop/ui dans angular.json (on le compile avec ng build @shop/ui).

npx ng generate library @shop/ui --project-root libs/ui

Le package.json de la bibliothèque reçoit "name": "@shop/ui", et le tsconfig l'alias "@shop/ui": ["./dist/shop/ui"] : le scope devient un sous-dossier de dist/.

Importer la bibliothèque, et le piège de dist/

La bibliothèque générée contient un composant d'exemple inutile ici : on supprime libs/models/src/lib/models.ts et libs/models/src/lib/models.spec.ts, puis on crée le modèle Product dans un nouveau fichier.

shop/libs/models/src/lib/product.ts
export interface Product {
  id: number;
  title: string;
  price: number;
// ...
}

La façade public-api.ts exporte désormais ce fichier à la place du composant supprimé.

shop/libs/models/src/public-api.ts
export * from './lib/product';

Une application importe le modèle par son alias, jamais par un chemin relatif qui remonterait dans libs/. Dans apps/fo/src/app/app.ts, le composant racine affiche un produit typé par Product (son template, un simple paragraphe, n'est pas reproduit).

shop/apps/fo/src/app/app.ts
import { Component, signal } from '@angular/core';
import { RouterOutlet } from '@angular/router';
import { Product } from '@shop/models'; // un alias, pas un chemin relatif
// ...
export class App {
  protected readonly product = signal<Product>({ id: 1, title: 'Clavier', price: 49 });
}

Tant que l'alias pointe vers ./dist/models, la bibliothèque doit être compilée avant l'application. Sans cela, ng build fo échoue.

Pointer vers les sources plutôt que vers dist/

L'alias n'est qu'une ligne de tsconfig : on peut le faire pointer vers le public-api.ts de la bibliothèque. L'application compile alors les sources de la bibliothèque comme les siennes, sans étape ng build models. C'est ce que fait Nx par défaut. Le tsconfig ci-dessous montre les deux écritures côte à côte.

shop/tsconfig.json
"paths": {
  "@shop/models": ["./libs/models/src/public-api.ts"],
  "@shop/ui": ["./dist/shop/ui"]
},

On l'a vérifié : après suppression de dist/, ng build fo réussit avec l'alias vers les sources ; et pendant un ng serve fo, modifier libs/models/src/lib/product.ts déclenche aussitôt une nouvelle Application bundle generation complete, sans watcher de bibliothèque à lancer à côté.

3Ranger les bibliothèques

Une fois qu'on sait créer une bibliothèque, la question devient : combien, et lesquelles ? Une seule bibliothèque shared finit souvent en fourre-tout que tout le monde importe. La convention répandue, popularisée par Nx, classe chaque bibliothèque par type, et chaque type a le droit de dépendre de certains autres seulement.

TypeContientExemple dans la boutiquePeut dépendre de
featuredes pages et composants « intelligents » d'un cas d'usage, souvent chargés en lazyfeature-products : la liste et le filtrefeature, ui, data-access, util, models
uides composants de présentation : ils reçoivent des données par input() et émettent par output()ui : la carte produit, la grilleui, util, models
data-accessles services qui parlent à l'API, l'état (signals, store)data-access : ProductsServicedata-access, util, models
utildes fonctions pures, des pipes, des validateursutil-format : formatage de prixutil, models
modelsdes interfaces et des types, aucun code exécutémodels : Productrien (ou models)

Le schéma suivant dessine ces règles. Les dépendances descendent toujours : une application importe des features, qui importent les couches du dessous ; rien ne remonte.

Pourquoi une bibliothèque ui ne doit-elle pas dépendre de data-access ? Prenons une carte produit qui injecterait ProductsService pour charger son produit elle-même.

  • Elle n'est plus réutilisable : le back-office affiche les mêmes produits depuis une autre API, ou depuis un brouillon non enregistré ; la carte, elle, va toujours chercher le sien.
  • Elle n'est plus testable simplement : pour afficher une carte dans un test, il faut maintenant simuler HTTP.
  • Elle tire toute la chaîne : importer un simple composant d'affichage embarque le client HTTP, l'URL de l'API, l'état.

La bonne répartition : la feature injecte le service et passe les données ; la carte ui ne connaît que input() et output(). Les noms de dossiers rendent le type visible : libs/shop/feature-products, libs/shop/ui, libs/shop/data-access, libs/shared/models, le premier niveau donnant le domaine (le scope).

Le CLI Angular, lui, ne vérifie rien de tout cela : un import de data-access dans ui compile sans un mot. C'est une convention à faire respecter en revue de code, ou par un outil ; c'est précisément ce qu'ajoute Nx, section suivante.

À retenir Cinq types de bibliothèques : feature, ui, data-access, util, models. Les dépendances descendent : feature => ui / data-access => util => models. Une ui reçoit ses données par input() et ne dépend jamais de data-access. Le CLI ne fait pas respecter ces règles ; Nx sait le faire.

4Nx, en comparaison

Nx est un outil de monorepo : il reprend le workspace qu'on vient de construire et ajoute ce qui manque quand il grossit. Il connaît le graphe des dépendances entre projets, il fait respecter les règles de la section 3, il ne recompile et ne reteste que ce qui est touché par un changement, et il met les résultats en cache. La dernière version publiée sur npm est Nx 23.3.0 (13 octobre 2026). Cette section ne monte pas un projet Nx complet ; elle montre le graphe, les règles, affected (avec le cache) et les générateurs sur un workspace réel, créé par la commande suivante.

npx create-nx-workspace@23.3.0 nxshop --preset=angular-monorepo --appName=fo --bundler=esbuild --style=css \
  --e2eTestRunner=none --unitTestRunner=none --ssr=false --linter=eslint --formatter=none \
  --aiAgents=none --nxCloud=skip --analytics=false --packageManager=npm --interactive=false

En 23.3.0, ce preset est redirigé vers un modèle tout fait (la sortie l'annonce : Mapping legacy preset 'angular-monorepo' to template 'nrwl/angular-template'), qui installe nx 23.2.0 et Angular 22.1, et ignore une partie des options. Ce modèle est une boutique : une application shop, une API Node (api, products) et des bibliothèques rangées dans packages/ plutôt que libs/, nommées feature-products, shared-ui, data et models, soit les types feature, ui, data-access et models de la section 3. Toutes les sorties de cette section viennent de ce workspace.

Tags et @nx/enforce-module-boundaries

Chaque projet porte des tags dans son project.json : un scope (le domaine) et un type (la couche). Dans le workspace de vérification, les types du modèle ont été renommés type:data-access et type:models pour suivre le vocabulaire de la section 3.

nxshop/packages/shop/shared-ui/project.json
"name": "shared-ui",
// ...
"tags": ["scope:shop", "type:ui"],

La règle ESLint @nx/enforce-module-boundaries traduit ensuite le tableau de la section 3 en contraintes : un projet qui porte le tag de gauche (sourceTag) ne peut importer que des projets portant l'un des tags de droite.

nxshop/eslint.config.mjs
'@nx/enforce-module-boundaries': [
  'error',
  {
    // ...
    depConstraints: [
      // ...
      {
        sourceTag: 'type:ui',
        onlyDependOnLibsWithTags: ['type:ui', 'type:util', 'type:models'],
      },
      {
        sourceTag: 'type:data-access',
        onlyDependOnLibsWithTags: ['type:data-access', 'type:util', 'type:models'],
      },

Pour vérifier, on ajoute dans la carte produit de shared-ui un import de ProductsService, qui vient de data, puis on lance le lint de shared-ui. Il refuse l'import et cite la règle enfreinte.

$ npx nx lint shared-ui
packages/shop/shared-ui/src/lib/product-card/product-card.component.ts
  9:1   error    A project tagged with "type:ui" can only depend on libs tagged with "type:ui", "type:util", "type:models"  @nx/enforce-module-boundaries
  9:10  warning  'ProductsService' is defined but never used                                                                @typescript-eslint/no-unused-vars

✖ 2 problems (1 error, 1 warning)

 NX   Running target lint for project shared-ui failed

Avec ce même import, npx nx build shop réussit (Successfully ran target build for project shop) : seul le lint voit la violation. C'est pourquoi ce lint tourne en intégration continue, au même titre que les tests.

affected : ne traiter que ce qui a changé

Grâce au graphe, Nx sait quels projets sont touchés par un fichier modifié : le projet du fichier et tous ceux qui en dépendent. L'option --files simule un changement ; sans elle, Nx compare la branche courante à main.

$ npx nx show projects --affected --files=packages/shop/shared-ui/src/lib/product-card/product-card.component.ts
["shared-ui","feature-product-detail","shop","shop-e2e","feature-products"]

$ npx nx show projects --affected --files=packages/shared/models/src/index.ts
["models","feature-product-detail","shop","shop-e2e","feature-products","shared-ui","products","api","data"]

Toucher shared-ui concerne 5 projets ; toucher models, dont tout le monde dépend, en concerne 9. La commande nx affected -t <cible> lance une cible (lint, test, build) sur ces projets seulement, et le cache évite de refaire un travail déjà fait. Au premier lancement, seul shared-ui, linté juste avant, vient du cache ; au second, rien n'est réexécuté.

$ npx nx affected -t lint --files=packages/shop/shared-ui/src/lib/product-card/product-card.component.ts
 NX   Successfully ran target lint for 5 projects
  Cache:             1/5 hit (20%)

$ npx nx affected -t lint --files=packages/shop/shared-ui/src/lib/product-card/product-card.component.ts
Nx read the output from the cache instead of running the command for 5 out of 5 tasks.
  Cache:             5/5 hit (100%)

En pratique : quelques applications et bibliothèques dans une équipe, le CLI suffit. Beaucoup de projets, plusieurs équipes et une CI qui devient lente, Nx rentabilise vite son coût d'entrée.

À retenir Nx ajoute au workspace : le graphe des projets (nx graph), des règles de dépendance vérifiées par le lint (tags + @nx/enforce-module-boundaries), nx affected pour ne traiter que ce qui a changé, un cache de tâches et des générateurs. Le build ne voit pas les violations de règles : c'est le lint qui les arrête.

5Micro-frontends : quand, et à quel prix

Au palier 2, toutes les applications d'un workspace sont compilées avec les bibliothèques qu'elles importent ; publier une modification du catalogue, c'est recompiler et redéployer l'application qui l'affiche. Les micro-frontends retirent cette contrainte : le catalogue devient une application à part, déployée par son équipe quand elle le veut, et l'application hôte va le chercher dans le navigateur, au moment où l'utilisateur ouvre la page.

Quand ça vaut le coup, et ce que ça coûte

Le gain est organisationnel, les coûts sont techniques. Le tableau met les deux en face.

Ce qu'on gagneCe que ça coûte
Des équipes qui livrent sans se synchroniser : chaque remote a son dépôt ou son dossier, sa CI, son rythmeLes versions partagées : Angular, RxJS et les bibliothèques communes doivent rester compatibles entre le shell et tous les remotes
Un déploiement plus petit et moins risqué : on ne redéploie que le remote modifiéDes pannes à l'exécution : un remote arrêté ou incompatible ne se voit pas à la compilation, mais dans le navigateur de l'utilisateur
Une migration progressive : une partie de l'écran peut changer de version, voire de frameworkLa cohérence de l'UX : styles, composants et comportements doivent rester alignés entre équipes
Des applications autonomes, lançables seules pour le développementLa session en double : si le service de session n'est pas partagé, chaque remote a la sienne (démontré en section 6)

Si une seule équipe livre tout en même temps, ces coûts n'achètent rien : un workspace avec des routes lazy fait le même travail.

Module Federation et Native Federation partagent le même modèle et presque les mêmes mots, résumés ici avec l'exemple de la section 6.

host (hôte, ou shell)l'application que l'utilisateur ouvre ; elle charge les remotesshell, sur le port 4400
remoteune application compilée et déployée à part, qui expose des morceauxmfe1, sur le port 4401
exposed moduleun fichier qu'un remote rend chargeable, sous une clé'./Component' => le composant Catalog
remoteEntryla carte d'identité d'un remote : ce qu'il expose, ce qu'il partage, en quelles versions ; un remoteEntry.json en Native Federation, un remoteEntry.js en Module Federationhttp://localhost:4401/remoteEntry.json
import mapun standard du navigateur : une table JSON « nom de module => URL du fichier », qui permet d'écrire import … from '@angular/core' sans bundlerconstruite par le shell au démarrage
sharedune dépendance chargée une seule fois et utilisée par tous@angular/core, rxjs, @mf/session
singletonpour une dépendance partagée : une seule instance de la bibliothèque dans la page, même si les versions diffèrentsingleton: true : indispensable pour @angular/core
strictVersionsi la version fournie ne satisfait pas requiredVersion, échouer au lieu de seulement avertirstrictVersion: true ; requiredVersion: 'auto' dans la configuration devient '^22.2.0', lu dans le package.json

Le schéma suit ce qui se passe quand l'utilisateur ouvre /catalog dans le shell. Les numéros donnent l'ordre des requêtes, observées dans l'onglet réseau du navigateur.

À retenir Les micro-frontends se justifient par des équipes qui doivent livrer indépendamment. Ils coûtent : versions partagées à garder compatibles, pannes visibles seulement à l'exécution, cohérence de l'UX, état (session) à partager explicitement. Un host charge des modules exposés par des remotes ; les dépendances communes sont partagées en singleton.

Deux paquets d'Angular Architects mettent en place la fédération avec le CLI Angular. Ils partagent le modèle de la section 5, mais pas la façon de compiler : c'est ce qui décide lequel choisir.

Les lignes « Compilation » et « Chargement » côté Native Federation sont vérifiées dans le projet ci-dessous (angular.json généré, import map lue dans la page). Côté Module Federation, elles viennent du README de la 22.0.0, qui précise que ng update @angular-architects/module-federation migre de ngx-build-plus vers @angular-builders/custom-webpack ; cette migration n'a pas été exécutée ici. La suite construit un exemple complet avec Native Federation : un shell, un remote mfe1 qui expose un catalogue, et une bibliothèque de session partagée entre les deux.

2. Faire de mfe1 un remote

On installe d'abord le paquet, en dépendance de développement comme le fait son README, puis son schematic transforme une application existante. Ses options sont --project, --port, --type (remote, host ou dynamic-host) et --webcomponent (démarrer l'application comme un élément HTML personnalisé, non utilisé ici) ; --skip-confirmation est une option de ng add qui évite la question « installer ce paquet ? ». On commence par le remote : le shell, configuré ensuite, pourra ainsi le trouver.

npm i -D @angular-architects/native-federation@22.2.2
npx ng add @angular-architects/native-federation@22.2.2 --project mfe1 --port 4401 --type remote --skip-confirmation

Le paquet étant déjà installé, ng add passe directement au schematic, qui annonce le passage au builder esbuild et liste les fichiers touchés.

Le schematic a aussi modifié angular.json : la cible build passe au builder de fédération, qui appelle le builder esbuild d'origine, renommé. (esbuild est le compilateur utilisé par défaut par le CLI depuis Angular 17 ; webpack est celui d'avant.)

  {},
  {

  },
)
  .catch((err) => console.error(err))
  .then((_) => import('./bootstrap'))
  .catch((err) => console.error(err));

3. Une bibliothèque de session, commune aux deux

Le shell connectera l'utilisateur et le remote affichera son nom : les deux doivent lire le même signal. La session vit donc dans une bibliothèque du workspace, générée comme en section 2.

npx ng generate library @mf/session --project-root libs/session

Comme pour models, on supprime le composant d'exemple (libs/session/src/lib/session.ts et son session.spec.ts) et on fait pointer l'alias vers les sources, dans le tsconfig.json du workspace : "@mf/session": ["./libs/session/src/public-api.ts"]. Le service, dans un nouveau fichier, affiche en plus un identifiant tiré au hasard, pour compter les instances.

mf/libs/session/src/lib/session.service.ts
import { Injectable, signal } from '@angular/core';

// L'utilisateur connecté, lu par le shell ET par le remote.
@Injectable({ providedIn: 'root' })
export class SessionService {
  readonly id = Math.random().toString(36).slice(2, 6); // pour voir combien d'instances existent
  readonly user = signal<string | null>(null);

  login(name: string) {
    this.user.set(name);
  }
  logout() {
    this.user.set(null);
  }
}

La façade de la bibliothèque l'exporte.

mf/libs/session/src/public-api.ts
export * from './lib/session.service';

6. Charger le remote dans une route

Côté shell, le remote se charge comme une route lazy, mais avec loadRemoteModule(nomDuRemote, cléExposée) à la place de import(). En 22.2.2, la fonction à utiliser est celle que renvoie initFederation : la fonction loadRemoteModule importée directement du paquet existe encore, mais ses types la marquent @deprecated (« Prefer the loadRemoteModule returned by the initFederation promise »). Ce résultat n'existe qu'une fois initFederation terminé, alors que les routes sont construites au démarrage : il faut donc le faire passer jusqu'aux routes, en trois petites modifications du code généré. D'abord, main.ts transmet le résultat à bootstrap.

mf/apps/shell/src/main.ts
import { initFederation } from '@angular-architects/native-federation';

// 1. lire le manifeste (où sont les remotes), 2. démarrer l'app en lui passant le résultat
initFederation('federation.manifest.json', {
  hostRemoteEntry: { url: './remoteEntry.json' },
})
  .then((nf) => import('./bootstrap').then((m) => m.bootstrap(nf)))
  .catch((err) => console.error(err));

Ensuite, bootstrap.ts et app.config.ts le passent jusqu'à provideRouter : la configuration devient une fonction qui reçoit ce résultat. Le type NativeFederationResult s'importe du paquet lui-même.

mf/apps/shell/src/bootstrap.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { NativeFederationResult } from '@angular-architects/native-federation';
import { appConfig } from './app/app.config';
import { App } from './app/app';

export const bootstrap = (nf: NativeFederationResult) =>
  bootstrapApplication(App, appConfig(nf));
mf/apps/shell/src/app/app.config.ts
import { NativeFederationResult } from '@angular-architects/native-federation';
// ...
// la config devient une fonction : les routes ont besoin du résultat de initFederation
export const appConfig = (nf: NativeFederationResult): ApplicationConfig => ({
  providers: [provideBrowserGlobalErrorListeners(), provideRouter(routes(nf))],
});

Enfin, les routes reçoivent ce résultat et en tirent loadRemoteModule. Le .catch affiche un composant de repli si le remote ne répond pas ; on le vérifie plus bas en arrêtant mfe1.

mf/apps/shell/src/app/app.routes.ts
import { Type } from '@angular/core';
import { Routes } from '@angular/router';
import { NativeFederationResult } from '@angular-architects/native-federation';
import { Home } from './home';
import { RemoteUnavailable } from './remote-unavailable';

export const routes = ({ loadRemoteModule }: NativeFederationResult): Routes => [
  { path: '', component: Home },
  {
    path: 'catalog',
    // chargé à l'exécution depuis mfe1 (http://localhost:4401), comme une route lazy
    loadComponent: () =>
      loadRemoteModule<{ Catalog: Type<unknown> }>('mfe1', './Component')
        .then((m) => m.Catalog)
        .catch(() => RemoteUnavailable), // le remote est arrêté ou en erreur
  },
];

Les deux composants locaux de ces routes sont minimes : Home affiche « Accueil du shell. », RemoteUnavailable le message de repli.

mf/apps/shell/src/app/remote-unavailable.ts
import { Component } from '@angular/core';

@Component({
  selector: 'app-remote-unavailable',
  template: `<p>Le catalogue est momentanément indisponible.</p>`,
})
export class RemoteUnavailable {}

Le composant racine du shell (son app.html et son app.css générés sont supprimés) ajoute un en-tête : deux liens, la session vue par le shell et un bouton de connexion.

mf/apps/shell/src/app/app.ts

import { SessionService } from '@mf/session';

@Component({
  imports: [RouterOutlet, RouterLink],

}

L'ancienne écriture, import { loadRemoteModule } from '@angular-architects/native-federation' puis loadRemoteModule({ remoteName: 'mfe1', exposedModule: './Component' }), a aussi été essayée sur une route de test : elle compile et affiche le catalogue. On la rencontre dans le code écrit pour les versions précédentes du paquet.

8. La session partagée : singleton ou pas

Native Federation partage par défaut les alias du tsconfig (ses shared mappings), comme des dépendances npm, en singleton. Le remoteEntry.json du build de mfe1 le montre, à côté d'Angular ; la version de @mf/session vient du package.json de la bibliothèque.

mf/dist/mfe1/browser/remoteEntry.json
"$version": "v4",
"name": "mfe1",
"shared": [
  {
    "packageName": "@angular/core",
    "outFileName": "_angular_core.3ZbNlBnnMw.js",
    "requiredVersion": "^22.2.0",
    "singleton": true,
    "strictVersion": true,
    "version": "22.2.2",
    "bundle": "browser-angular_core"
  },
  // ...
  {
    "packageName": "@mf/session",
    "outFileName": "_mf_session-CI2GQ7ZM.js",
    "requiredVersion": "~0.0.1",
    "singleton": true,
    "strictVersion": true,
    "version": "0.0.1",
    "bundle": "mapping-bundle"
  }

Pour voir ce que ce partage apporte, on refait l'essai en désactivant le partage des alias dans mfe1 : l'option sharedMappings liste les alias à partager, et une liste vide n'en partage aucun. On relance ng serve mfe1, puis on remet la configuration d'origine.

mf/apps/mfe1/federation.config.mjs (expérience)
// EXPÉRIENCE : ne pas partager les libs du workspace (@mf/session)
sharedMappings: [],

Voici ce qu'affiche la page dans les deux cas, après « Se connecter (Alice) » dans le shell puis ouverture du catalogue.

Partagée (configuration générée)Non partagée (sharedMappings: [])
Le shell afficheAlice (instance quh9)Alice (instance 8keg)
Le remote afficheAlice (instance quh9)anonyme (instance y1jk)
« Se déconnecter depuis le remote »le shell repasse aussi à « anonyme »sans effet sur le shell
Pourquoiun seul fichier _mf_session.js, celui du shell ; une seule classe SessionService, donc une seule instance dans l'injecteur racineremoteEntry.json ne mentionne plus @mf/session : le remote embarque sa propre copie de la classe. L'injecteur range chaque service sous sa classe : deux classes, donc deux instances

C'est la « session en double » de la section 5 : chaque copie de la bibliothèque a son propre signal. La même chose arriverait avec deux copies de @angular/core, en pire, d'où le singleton: true sur Angular.

strictVersion n'a pas été mis à l'épreuve : dans un seul workspace, le shell et le remote ont forcément les mêmes versions. Le conflit apparaît quand le remote est compilé ailleurs, avec un @angular/core qui ne satisfait pas le requiredVersion du shell ; c'est l'erreur à surveiller lors d'une montée de version non coordonnée.

9. Quand le remote est arrêté

Dernier essai : arrêter ng serve mfe1 et recharger le shell. Le shell démarre quand même (la console note net::ERR_CONNECTION_REFUSED) ; c'est l'ouverture du catalogue qui échoue, avec cette erreur dans la console.

ERROR NFError: Failed to load module mfe1/./Component
    at loadRemoteModule (...)
    at Object.loadComponent (...)

Sans le .catch de la route, la navigation est simplement annulée : l'utilisateur clique, et rien ne se passe. Avec, la page affiche « Le catalogue est momentanément indisponible. » C'est la panne à l'exécution de la section 5, qu'aucune compilation ne détecte.

À retenir ng add @angular-architects/native-federation --project <app> --port <n> --type remote|dynamic-host génère federation.config.mjs, coupe le démarrage en main.ts + bootstrap.ts et, pour un hôte dynamique, crée public/federation.manifest.json. En 22.2, on utilise le loadRemoteModule renvoyé par initFederation, avec un repli en cas d'échec. Ce qui doit être unique (Angular, la session) se partage en singleton ; une bibliothèque non partagée est dupliquée, et son état avec.

7Récap : choisir son palier

Le tableau donne un choix par défaut pour les situations les plus courantes.

SituationChoix par défautPourquoi
Une application, une équipe, même grossepalier 1 : une route lazy par featurerien à synchroniser ; le lazy loading suffit pour la performance
Plusieurs applications (vitrine, back-office) qui partagent modèles et composantspalier 2 : workspace CLI, apps/ + libs/, alias @scope/…code commun écrit une fois, chaque application déployée à part
Le workspace grossit, la CI devient lente, les règles entre libs ne sont plus respectéespalier 2 avec Nxaffected, cache, enforce-module-boundaries
Plusieurs équipes qui doivent livrer sans se synchroniser, nouveau projet Angular 22palier 3 : Native Federationgarde le builder esbuild du CLI, standards du navigateur
Micro-frontends existants en webpack (Angular 20)rester en Module Federation, monter de version avec ng updatepas de réécriture ; Native Federation reste une option pour plus tard (paquet -v4 pour Angular 20 et 21)

Quel que soit le palier, les mêmes règles valent : des bibliothèques rangées par type, une ui qui ne parle pas à l'API, et ce qui doit être unique (la session, Angular lui-même) partagé explicitement.

Pour pratiquer : le lab Minishop (en cours d'écriture). Les autres synthèses du jour 3 : authentification et gestion d'état.

À retenir On monte de palier pour des raisons d'équipes et de déploiement. Workspace CLI d'abord ; Nx quand il faut un graphe, des règles et affected ; micro-frontends seulement si des équipes doivent livrer indépendamment, avec Native Federation sur un projet Angular 22 neuf et Module Federation sur un existant webpack.
