# 🗄️ 06 — Le BO minimal

> **Scénario semi-autonome, environ 20 minutes.** Aux étapes précédentes, vous avez été guidé pas à
> pas pour acquérir les bases : store, session, intercepteur, guard. Vous pouvez maintenant aborder
> le back-office plus librement : moins de code à trous, davantage de « même schéma que l'étape
> X », et les liens de doc. Le BO réutilise tout : la session et la page de connexion de
> `@shop/auth`, la liste de `@shop/products`, l'en-tête de `@shop/ui`. Une seule pièce est
> nouvelle, un guard de **rôle** posé en `canMatch`. La solution est dans `solution/apps/bo/` et
> `solution/libs/auth/src/lib/guards/role.guard.ts`.

## ✨ Objectifs

- Écrire une **fabrique de guard**, `roleGuard('admin')`, qui renvoie un `CanMatchFn`.
- Comprendre `canMatch` : sans le rôle, le code de la page n'est **même pas téléchargé**.
- Constater l'intérêt du workspace : une bibliothèque, deux applications.
- Vérifier que le **serveur** décide : une écriture refusée au `curl` (`403`, `401`).

## 📁 Point de départ

Vous partez du BO de l'étape 01 : un en-tête et une page d'accueil statique. Le BO n'a pas encore
de configuration HTTP, ni de session. À la fin de cette étape, il ressemble à ceci :

```
libs/auth/src/lib/guards/role.guard.ts      roleGuard(role), une fabrique de CanMatchFn (section 1)
apps/bo/src/app/
├── app.config.ts                           provideApi + provideAuth, comme le FO (section 2)
├── app.routes.ts                           '' sous roleGuard('admin') en canMatch, 'login', '**' (section 3)
├── app.ts, app.html                        le menu « Produits » et le bouton de session (section 4)
└── pages/home/                             lib-product-list, en lecture seule (section 4)
```

Relancez le BO dans le terminal 3 (`npm run bo`, sur http://localhost:4201), en plus de l'API
(terminal 1) et du FO (terminal 2).

## 🏭 1 — Une fabrique de guard : `roleGuard(role)`

`authGuard` répondait à une question fixe, « est-on connecté ? ». Ici, la question dépend d'un
paramètre, le rôle exigé. On écrit donc une **fabrique** : une fonction qui reçoit le rôle et
**renvoie** le guard. Dans la route, on écrira `roleGuard('admin')`.

Ce guard sera posé en `canMatch`, et non en `canActivate`. La différence est visible dans l'onglet
Réseau :

| Clé | Moment | Conséquence pour une route en `loadComponent` |
|---|---|---|
| `canActivate` | **après** que le routeur a retenu la route | le fichier JavaScript de la page est téléchargé, puis l'accès est refusé |
| `canMatch` | **pendant** que le routeur choisit la route | sans le rôle, la route n'est pas retenue : le fichier de la page n'est **jamais demandé** |

Générez le guard dans `@shop/auth`, en précisant le type avec `--implements` :

```bash
npx ng generate guard guards/role --type-separator=. --implements CanMatch --project @shop/auth --skip-tests
```

Un `CanMatchFn` ne reçoit pas l'URL complète, mais la route et la liste des **segments** de
l'adresse (`/a/b` donne les segments `a` et `b`) : pour `returnUrl`, il faut la recomposer. La CLI
a généré une constante `roleGuard: CanMatchFn` qui laisse toujours passer, pas une fabrique :
remplacez **tout le contenu** de `libs/auth/src/lib/guards/role.guard.ts` par ce squelette, puis
écrivez le corps à partir des indices qui suivent.

🚧 **À compléter :**

```ts
import { inject } from '@angular/core';
import { CanMatchFn, Router } from '@angular/router';
import { SessionStore } from '../services/session.store';

/**
 * Une FABRIQUE de guard : roleGuard('admin') renvoie un CanMatchFn qui exige ce rôle.
 * Sans le rôle, page de connexion (avec returnUrl) : on peut y changer de compte.
 */
export function roleGuard(role: string): CanMatchFn {
  return (_route, segments) => {
    // TODO : la session et le routeur, par inject()
    // TODO : si la session a le rôle, true
    // TODO : sinon, returnUrl = '/' + les segments joints par '/', et un UrlTree vers ['/login']
  };
}
```

Les indices :

| Besoin | Indice |
|---|---|
| tester le rôle | `session.hasRole(role)` : la **règle** écrite à l'étape 04, celle que le menu utilisera aussi |
| recomposer l'adresse | `segments.map((segment) => segment.path).join('/')` ; pour l'accueil, la liste est vide et l'on obtient `'/'` |
| rediriger | `router.createUrlTree(['/login'], { queryParams: { returnUrl } })`, comme dans `authGuard` |

Exportez-le dans `libs/auth/src/public-api.ts`, sous la ligne de `auth.guard`.

> ℹ️ **Pourquoi la page de connexion, et pas une page « accès refusé » ?** Si `alice` arrive sur le
> BO, elle est déjà connectée, mais sans le bon rôle : la page de connexion le lui dit (« Vous êtes
> connecté en tant que alice : cette page demande un autre compte. », étape 04) et lui permet de
> changer de compte.

> 📖 [`CanMatchFn`](https://angular.dev/api/router/CanMatchFn) ·
> [Synthèse authentification : les guards](https://bngams.github.io/2610-ng/03-intro-auth/)

## ⚙️ 2 — La configuration du BO

Le BO a besoin des mêmes briques que le FO : `HttpClient` avec les deux intercepteurs, l'adresse de
l'API, et la session chargée au démarrage. Même schéma que l'étape 04, section 6.1, dans
`apps/bo/src/app/app.config.ts` :

1. importez `provideApi` depuis `@shop/api`, et `authInterceptor` et `provideAuth` depuis
   `@shop/auth` ;
2. ajoutez aux providers `provideApi({ url: '/api', interceptors: [authInterceptor] })` et
   `provideAuth()`.

Le BO n'a pas de paramètre de route à lier : `provideRouter(routes)` suffit, sans
`withComponentInputBinding()`.

Le proxy est déjà en place depuis l'étape 02 : la cible `serve` du projet `bo` pointe vers le même
`proxy.conf.json` que le FO.

## 🛣️ 3 — Les routes : l'accueil sous `roleGuard('admin')`

C'est le cœur de l'étape. L'accueil du BO est chargé **à la demande** (`loadComponent`), et protégé
en `canMatch`. La page de connexion est celle de `@shop/auth`, exactement comme dans le FO.
Remplacez le contenu de `apps/bo/src/app/app.routes.ts` :

```ts
import { Routes } from '@angular/router';
import { Login, roleGuard } from '@shop/auth';
import { NotFound } from './pages/not-found/not-found';

export const routes: Routes = [
  {
    path: '',
    pathMatch: 'full',
    // canMatch est évalué AVANT loadComponent : sans le rôle, le fichier de la page n'est même pas téléchargé
    canMatch: [roleGuard('admin')],
    loadComponent: () => import('./pages/home/home').then((m) => m.Home),
  },
  { path: 'login', component: Login }, // la page de connexion de @shop/auth, comme dans le FO
  { path: '**', component: NotFound },
];
```

Deux détails comptent :

| Détail | Pourquoi |
|---|---|
| `pathMatch: 'full'` | le chemin vide est un préfixe de **toutes** les adresses : `pathMatch: 'full'` réserve cette route à l'adresse vide exactement, et son guard ne concerne que l'accueil |
| `Home` n'est plus importé en haut du fichier | un `import` statique mettrait la page dans le bundle principal, et `loadComponent` ne servirait plus à rien |

## 🧩 4 — L'accueil et l'en-tête du BO

L'accueil du BO affiche la liste des produits, **en lecture seule** : c'est `ProductList` de
`@shop/products`, la même bibliothèque que celle du catalogue du FO. Deux fichiers changent dans
`apps/bo/src/app/pages/home/` :

1. dans `home.ts`, ajoutez `import { ProductList } from '@shop/products';` et mettez
   `imports: [ProductList]` dans le décorateur ;
2. dans `home.html`, remplacez le texte du paragraphe par « Les produits de la boutique, en lecture
   seule. », et ajoutez `<lib-product-list />` dessous. Gardez le commentaire de la première ligne :
   l'emplacement de la bannière reste réservé pour l'étape 08.

L'en-tête du BO suit le schéma du FO, avec ses propres choix :

1. dans `app.html`, l'en-tête entoure `<lib-session-button />` (le BO n'a pas de panier) ;
2. dans `app.ts`, importez `inject` depuis `@angular/core`, et `SessionButton` et `SessionStore`
   depuis `@shop/auth` ; ajoutez `SessionButton` au tableau `imports` du décorateur ;
3. toujours dans `app.ts`, déclarez `private readonly session = inject(SessionStore);` **avant**
   `menu` (comme dans le FO à l'étape 05, la fonction `visible` l'utilise), et donnez au menu un seul
   lien, `{ title: 'Produits', path: '/', visible: () => this.session.hasRole('admin') }` : la
   **même règle** que le `roleGuard('admin')` de la route.

> 📖 [`loadComponent`](https://angular.dev/guide/routing/define-routes#lazily-loaded-components-and-routes)

## 🚀 5 — Vérifier

Compilez le BO :

```bash
npx ng build bo
```

L'accueil apparaît comme un fichier à part, `home`, dans les **Lazy chunk files** :

```
Lazy chunk files    | Names         |  Raw size | Estimated transfer size
chunk-RKK2QXXX.js   | home          |  11.46 kB |                 2.76 kB
```

### 5.1 — Avec `alice`, puis avec `admin`

Dans le navigateur, gardez l'onglet **Réseau** ouvert, filtré sur `JS`.

> 💡 **Tester :**
> 1. Connectez-vous en `alice` sur le FO (http://localhost:4200), puis ouvrez
>    http://localhost:4201. Le BO vous envoie sur `/login?returnUrl=%2F`, l'en-tête affiche déjà
>    « alice », et la page dit « Vous êtes connecté en tant que alice : cette page demande un autre
>    compte. » Le menu n'affiche pas « Produits ».
> 2. Dans l'onglet Réseau, seuls `main.js` et un `chunk-….js` initial ont été chargés : le fichier
>    de l'accueil (celui que le serveur de développement liste sous le nom `home` dans le terminal
>    3) n'a **jamais** été demandé.
> 3. Connectez-vous en `admin` / `admin` : retour sur `/`, la liste des trente produits s'affiche,
>    **sans** bouton « Ajouter », et l'onglet Réseau montre enfin le fichier de l'accueil. Le menu
>    affiche « Produits ».
> 4. « Se déconnecter » : retour sur `/login?returnUrl=%2F`, la liste a disparu.

Pourquoi `alice` était-elle déjà connectée sur le BO ? Un cookie est lié au **nom d'hôte**, pas au
port : `localhost:4200` et `localhost:4201` partagent le cookie `sid`. Se connecter sur l'une des
applications connecte donc aussi l'autre, et changer de compte sur le BO change aussi le compte du
FO. En production, avec deux noms de domaine distincts (`shop.example.com`, `admin.example.com`),
ce ne serait pas le cas.

> ℹ️ **La page se recharge toute seule une fois ?** La première fois qu'une page chargée à la
> demande utilise de nouvelles dépendances, le serveur de développement peut afficher
> `optimized dependencies changed. reloading` dans le terminal 3 et recharger le navigateur. C'est
> un comportement de Vite, en développement seulement : recommencez l'action.

### 5.2 — Le serveur décide : le refus au `curl`

Les guards ont masqué la page à `alice`, mais rien ne l'empêche d'appeler l'API elle-même. C'est
le serveur qui doit refuser, et il le fait. Dans le terminal 4, celui des commandes, connectez-vous en
`alice` avec `curl`, en gardant le cookie dans un fichier (`-c`) :

```bash
curl -s -c alice.cookies -o /dev/null -X POST http://localhost:4200/api/auth/login -H 'Content-Type: application/json' -d '{"username":"alice","password":"alice"}'
```

Avec ce cookie (`-b`), tentez de supprimer un produit :

```bash
curl -si -b alice.cookies -X DELETE http://localhost:4200/api/products/1
```

Le serveur refuse avec un `403` : `alice` est connectée, mais n'a pas le rôle `admin`.

```
HTTP/1.1 403 Forbidden
...
{
  "error": "Réservé au rôle admin"
}
```

Sans cookie du tout, la même requête est refusée plus tôt, avec un `401` :

```bash
curl -si -X DELETE http://localhost:4200/api/products/1
```

La réponse commence par `HTTP/1.1 401 Unauthorized` et se termine par
`{ "error": "Non authentifié" }`. Supprimez ensuite le fichier `alice.cookies`.

Ces trois essais résument le partage des rôles entre le navigateur et le serveur, que le tableau
suivant met côte à côte :

| Couche | Rôle | Contournable ? |
|---|---|---|
| le menu (`visible`) | ne pas proposer un lien inutile | oui : il suffit de taper l'adresse |
| le guard (`canMatch`) | ne pas afficher, ni même télécharger, une page inutile | oui : le code tourne dans le navigateur |
| le serveur (`401`, `403`) | **refuser** l'action | non : c'est la seule vraie barrière |

## 🧠 Récap

- `roleGuard('admin')` est une **fabrique** : une fonction qui renvoie un `CanMatchFn` paramétré.
- `canMatch` + `loadComponent` : sans le rôle, la route n'est pas retenue, et son code n'est pas
  téléchargé.
- Une bibliothèque, deux applications : le BO réutilise `auth`, `products` et `ui` sans rien
  recopier.
- Le menu et les guards font de l'ergonomie ; le **serveur** décide.
