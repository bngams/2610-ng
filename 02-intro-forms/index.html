Angular 22 — Les formulaires

Angular propose trois façons de construire un formulaire : template-driven, Reactive Forms et, depuis la v22 en version stable, Signal Forms. Cette page les compare, montre qui détient la valeur dans chacune, puis va jusqu'au formulaire construit à partir d'une description JSON. Chaque extrait de code est copié d'un projet Angular 22 qui compile (ng build) et dont le comportement décrit ici a été vérifié dans le navigateur ; ce projet de vérification n'est pas livré.

Imprimable : Ctrl/Cmd + P puis « Enregistrer en PDF ». Avant cette page, la synthèse du jour 1 et la démo HTTP. Pour pratiquer : Housing, premiers pas (parcours Init, avec un dossier de candidature en plusieurs étapes en Reactive Forms) et Housing sous pression asynchrone (parcours Avancé, qui migre ce dossier vers Signal Forms).

Le fil rouge est une candidature à un logement : nom, email, adresse, revenus, occupants. Les exemples sont volontairement petits, pour que chaque mécanisme se voie seul.

1Trois familles de formulaires

Un formulaire Angular doit faire trois choses : garder la valeur de chaque champ, la valider, et dire à l'écran si elle est valide. Les trois familles font les mêmes choses ; ce qui change, c'est où vit la valeur, donc où l'on écrit la validation et comment on la lit.

  • Template-driven (FormsModule) : on décrit le formulaire dans le HTML avec [(ngModel)] et des attributs comme required. C'est la plus ancienne ; elle n'est pas dépréciée en v22, mais on ne la choisit plus pour un nouveau formulaire complexe.
  • Reactive Forms (ReactiveFormsModule) : on crée le formulaire dans la classe, avec FormControl, FormGroup et FormArray, puis le HTML s'y branche. C'est le standard des projets v20 et antérieurs.
  • Signal Forms (@angular/forms/signals) : on part d'un signal qui contient les données, et form() en dérive les champs et leur validation. C'est la plus récente.

Le statut de Signal Forms dépend de la version, et c'est le point à vérifier avant de l'utiliser sur un projet existant.

À retenir Trois familles, une question : où vit la valeur ? Dans le template (template-driven), dans un objet FormControl de la classe (Reactive), ou dans un signal (Signal Forms). Signal Forms n'existe pas en v20, est expérimental en v21 et stable en v22.

2Fonctionnement dans Angular : qui détient la valeur

Dans les trois familles, une directive posée sur l'<input> fait le lien entre l'élément HTML et un objet qui garde la valeur et l'état (valide, touché…). La différence est de savoir qui crée cet objet, et si votre code peut le toucher directement. Les trois schémas suivants se lisent de la même façon : la classe du composant à gauche, le template à droite.

Template-driven : NgModel crée le FormControl

Ici, vous ne créez aucun contrôle. La directive NgModel en crée un, le garde pour elle, et l'enregistre auprès du NgForm posé automatiquement sur <form>. La classe ne connaît que l'objet applicant, synchronisé par [(ngModel)].

Reactive Forms : vous créez le FormControl, la directive s'y branche

Le sens est inversé : c'est la classe qui crée FormGroup et FormControl. Les directives [formGroup] et formControlName ne créent rien, elles se branchent sur ces instances. La classe y a donc un accès direct et immédiat.

Signal Forms : un signal, et un arbre de champs dérivé

Le point de départ est un signal qui contient les données. form(model, schema) en construit un arbre de champs : f.lastName est un champ, et f.lastName() donne son état sous forme de signals. La directive [formField] lit la valeur du champ et, à la saisie, écrit directement dans le signal du modèle.

À retenir Template-driven : NgModel crée le contrôle, vous n'y accédez qu'à travers lui. Reactive : vous créez le contrôle, [formControl] / formControlName s'y branche. Signal Forms : vous créez un signal, form() en dérive les champs, [formField] lit et écrit le signal.

3Template-driven

Pour un petit formulaire, tout tient dans le HTML. Le composant importe FormsModule, qui apporte les directives ngModel et ngForm, puis expose un simple objet que le formulaire va remplir.

src/app/template-driven/td-application.ts
import { AfterViewInit, Component, viewChild } from '@angular/core';
import { FormsModule, NgForm } from '@angular/forms';
import { JsonPipe } from '@angular/common';

@Component({
  selector: 'app-td-application',
  imports: [FormsModule, JsonPipe], // FormsModule apporte ngModel et ngForm
// ...
export class TdApplication implements AfterViewInit {
  // la source de vérité : un simple objet, modifié par [(ngModel)]
  applicant = { lastName: '', email: '' };

Le template fait le reste. Trois écritures sont à reconnaître : [(ngModel)] lie un champ à une propriété dans les deux sens (l'attribut name est obligatoire, c'est la clé du contrôle dans le formulaire), required et email sont des directives de validation, et #f="ngForm" donne un nom au NgForm qu'Angular pose sur <form>, pour lire f.valid ou f.value.

src/app/template-driven/td-application.ts
<!-- #f="ngForm" : une référence vers le NgForm qu'Angular pose sur <form> -->
<form #f="ngForm" (ngSubmit)="send(f)">
  <label>Nom
    <input name="lastName" [(ngModel)]="applicant.lastName" required #lastName="ngModel" />
  </label>
  @if (lastName.invalid && lastName.touched) {
    <small class="error">Le nom est obligatoire</small>
  }
  <label>Email
    <input name="email" type="email" [(ngModel)]="applicant.email" required email />
  </label>
  <button [disabled]="f.invalid">Envoyer</button>
</form>
<pre>f.valid = {{ f.valid }} · f.value = {{ f.value | json }}</pre>

Le revers apparaît dès qu'on veut lire le formulaire depuis la classe. NgModel enregistre ses contrôles de façon asynchrone : au moment de ngAfterViewInit, le formulaire est encore vide. Le composant de vérification le journalise.

src/app/template-driven/td-application.ts
// le NgForm du template, lu depuis la classe
private readonly ngForm = viewChild.required(NgForm);

ngAfterViewInit() {
  // NgModel enregistre ses FormControl de façon ASYNCHRONE : pas encore là
  console.log('[td] contrôles à AfterViewInit :', Object.keys(this.ngForm().controls));
  setTimeout(() => console.log('[td] un tour plus tard :', Object.keys(this.ngForm().controls)));
}

Dans la console du navigateur, la première ligne montre un formulaire encore vide, la seconde les deux contrôles enregistrés entre-temps.

[td] contrôles à AfterViewInit : []
[td] un tour plus tard : ['lastName', 'email']
À retenir FormsModule, [(ngModel)] + name, des attributs de validation, #f="ngForm" pour lire l'état. Simple pour quelques champs ; mais la valeur n'est pas typée et les contrôles n'existent qu'un tour après l'affichage, ce qui complique la logique et les tests dès que le formulaire grossit.

4Reactive Forms

Avec les Reactive Forms, le formulaire est d'abord un objet TypeScript. On le construit dans la classe, contrôle par contrôle, puis le template s'y branche. C'est ce que fait l'étape « formulaire » du tutoriel Housing, et c'est la famille la plus répandue dans les projets existants.

FormControl, FormGroup imbriqué et validateurs

Un FormControl tient une valeur ; un FormGroup regroupe des contrôles sous des clés, et peut en contenir un autre (ici l'adresse). Chaque contrôle reçoit ses validateurs : ceux d'Angular (Validators.required, Validators.email) ou les vôtres. Le second argument du groupe porte un validateur de groupe, qui voit tous les contrôles à la fois.

src/app/reactive/reactive-application.ts
export class ReactiveApplication {
  // on CRÉE les contrôles dans la classe : c'est eux la source de vérité
  readonly search = new FormControl('');

  readonly application = new FormGroup(
    {
      lastName: new FormControl('', Validators.required),
      email: new FormControl('', [Validators.required, Validators.email]),
      confirmEmail: new FormControl(''),
      address: new FormGroup({
        city: new FormControl(''),
        zip: new FormControl('', [Validators.required, zipCode]),
      }),
    },
    { validators: emailsMatch }, // validateur inter-champs, au niveau du groupe
  );

  send() {
    // accès synchrone : la valeur est là, tout de suite
    console.log('[reactive] envoyé', this.application.getRawValue());
  }
}

Un validateur est une simple fonction : elle reçoit le contrôle et renvoie null si tout va bien, ou un objet d'erreurs. Le premier exemple vérifie un seul champ ; le second, posé sur le groupe, compare deux champs frères, ce qu'un validateur de champ ne peut pas faire.

src/app/reactive/validators.ts
import { AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

// Validateur personnalisé sur UN champ : un code postal français = 5 chiffres.
export const zipCode: ValidatorFn = (control: AbstractControl): ValidationErrors | null =>
  /^\d{5}$/.test(control.value ?? '') ? null : { zipCode: { actual: control.value } };

// Validateur inter-champs, posé sur le GROUPE : il compare deux contrôles frères.
export const emailsMatch: ValidatorFn = (group: AbstractControl): ValidationErrors | null => {
  const email = group.get('email')?.value;
  const confirm = group.get('confirmEmail')?.value;
  return email === confirm ? null : { emailsMismatch: true };
};

Côté template, [formGroup] se pose sur <form>, formControlName sur chaque champ et formGroupName sur le bloc imbriqué. Un contrôle isolé, hors de tout groupe, se lie avec [formControl]. Les erreurs se lisent avec hasError(), sur le contrôle ou sur le groupe.

src/app/reactive/reactive-application.ts
<!-- un FormControl seul, sans groupe : [formControl] -->
<label>Recherche <input [formControl]="search" /></label>
<p>search.value = {{ search.value }}</p>
<!-- ... -->
<form [formGroup]="application" (ngSubmit)="send()">
  <label>Nom <input formControlName="lastName" /></label>
  @if (application.controls.lastName.hasError('required') && application.controls.lastName.touched) {
    <small class="error">Le nom est obligatoire</small>
  }
  <label>Email <input formControlName="email" /></label>
  <label>Confirmer l'email <input formControlName="confirmEmail" /></label>
  @if (application.hasError('emailsMismatch')) {
    <small class="error">Les deux emails diffèrent</small>
  }

  <!-- groupe imbriqué : formGroupName -->
  <fieldset formGroupName="address">
    <label>Ville <input formControlName="city" /></label>
    <label>Code postal <input formControlName="zip" /></label>
    @let zip = application.controls.address.controls.zip;
    @if (zip.hasError('zipCode') && zip.touched) {
      <small class="error">5 chiffres attendus</small>
    }
  </fieldset>
  <button [disabled]="application.invalid">Envoyer</button>
</form>

Typed forms : FormBuilder et NonNullableFormBuilder

Depuis la v14, les formulaires réactifs sont typés. Un détail surprend : reset() remet un contrôle à null, donc son type inclut null. NonNullableFormBuilder (ou l'option nonNullable: true) fait revenir reset() à la valeur initiale et retire le null du type. Le compilateur refuse alors une valeur du mauvais type : la ligne marquée @ts-expect-error provoque bien, sans ce commentaire, l'erreur TS2345: Argument of type 'string' is not assignable to parameter of type 'number'.

src/app/reactive/typed-forms.ts
export class TypedForms {
  // FormBuilder : le type inclut null, car reset() remet la valeur à null
  readonly city: FormControl<string | null> = inject(FormBuilder).control('Rennes');

  // NonNullableFormBuilder : reset() revient à la valeur initiale, pas de null
  readonly cityNonNullable: FormControl<string> = inject(NonNullableFormBuilder).control('Rennes');

  readonly rent = new FormControl(800, { nonNullable: true }); // FormControl<number>

  resetBoth() {
    this.city.reset(); // value = null
    this.cityNonNullable.reset(); // value = 'Rennes'
  }

  wrongType() {
    // @ts-expect-error : une chaîne dans un FormControl<number> ne compile pas
    this.rent.setValue('huit cents');
  }
}

Après un clic sur « reset() des deux », l'écran affiche city.value = null et cityNonNullable.value = Rennes.

FormArray : une liste de longueur variable

Un FormArray est une liste de contrôles dont la longueur change à l'exécution : ici, les occupants du logement. Le NonNullableFormBuilder injecté raccourcit l'écriture : fb.group({ cle: [valeur, validateurs] }). On ajoute avec push() et on retire avec removeAt().

src/app/reactive/occupants-form.ts
export class OccupantsForm {
  // NonNullableFormBuilder : chaque contrôle est créé avec nonNullable: true
  private readonly fb = inject(NonNullableFormBuilder);

  readonly household = this.fb.group({
    maxRent: [800, [Validators.required, Validators.min(300)]],
    occupants: this.fb.array([this.newOccupant()]),
  });

  // raccourci typé vers le FormArray
  get occupants() {
    return this.household.controls.occupants;
  }
  // ...
  newOccupant() {
    return this.fb.group({
      firstName: ['', Validators.required],
      age: [18, [Validators.required, Validators.min(0)]],
    });
  }

  addOccupant() {
    this.occupants.push(this.newOccupant());
  }

  removeOccupant(index: number) {
    this.occupants.removeAt(index);
  }

Dans le template, formArrayName désigne la liste et chaque élément est repéré par son index, avec [formGroupName]="i".

src/app/reactive/occupants-form.ts
<form [formGroup]="household">
  <label>Loyer max (€) <input type="number" formControlName="maxRent" /></label>
  <div formArrayName="occupants">
    @for (occupant of occupants.controls; track occupant; let i = $index) {
      <fieldset [formGroupName]="i">
        <input formControlName="firstName" placeholder="Prénom" />
        <input type="number" formControlName="age" placeholder="Âge" />
        <button type="button" (click)="removeOccupant(i)">Retirer</button>
      </fieldset>
    }
  </div>
  <button type="button" (click)="addOccupant()">Ajouter un occupant</button>
  <button type="button" (click)="household.reset()">Réinitialiser</button>
</form>

valueChanges, statusChanges et le pont vers les signals

Chaque contrôle expose deux Observables : valueChanges émet à chaque modification de valeur, statusChanges à chaque changement de statut. Pour les afficher ou les combiner avec des signals, toSignal fait le pont, comme dans la démo HTTP. Comme ces Observables n'émettent qu'au premier changement, on fournit une initialValue.

src/app/reactive/occupants-form.ts
// valueChanges / statusChanges sont des Observables : toSignal fait le pont vers les signals
readonly status = toSignal(this.household.statusChanges, { initialValue: this.household.status });
readonly occupantCount = toSignal(
  this.household.valueChanges.pipe(map((v) => v.occupants?.length ?? 0)),
  { initialValue: 1 },
);

Dans le navigateur, avec un occupant au départ : saisir son prénom fait passer le statut de INVALID à VALID ; « Ajouter un occupant » donne occupants = 2 et repasse INVALID (le nouveau prénom est vide) ; « Retirer » sur le premier ne garde que le second ; un loyer de 100 repasse INVALID (Validators.min(300)) ; « Réinitialiser » remet le loyer à 800 et le prénom à vide, les valeurs initiales, grâce au builder non nullable.

À retenir Vous créez les contrôles dans la classe (FormControl, FormGroup, FormArray), le template s'y branche ([formGroup], formControlName, formArrayName). Un validateur est une fonction ; s'il compare plusieurs champs, il se pose sur le groupe. Préférez NonNullableFormBuilder pour des types sans null, et toSignal pour passer de valueChanges aux signals.

5Signal Forms

Signal Forms reprend la même candidature avec une autre logique : on décrit d'abord les données, avec une interface et un signal, et tout le reste en découle. Le composant importe deux directives de @angular/forms/signals : FormField pour [formField] et FormRoot pour [formRoot].

src/app/signal/signal-application.ts
import { Component, signal } from '@angular/core';
import { JsonPipe } from '@angular/common';
import {
  applyEach, email, form, FormField, FormRoot, min, pattern, required, validate,
} from '@angular/forms/signals';

// 1. Le modèle : une interface, les données du formulaire
interface HousingApplication {
  lastName: string;
  email: string;
  confirmEmail: string;
  monthlyIncome: number;
  address: { city: string; zip: string };
  occupants: { firstName: string }[];
}
// ...
@Component({
  selector: 'app-signal-application',
  imports: [FormField, FormRoot, JsonPipe], // FormField = [formField], FormRoot = [formRoot]

Le modèle et le schéma

Le modèle est un signal qui contient toutes les valeurs de départ. form(model, schema, options) construit l'arbre de champs. Le schéma est une fonction qui reçoit p, le chemin vers chaque champ, et déclare les règles : required, email, min, pattern. Une règle personnalisée s'écrit avec validate, qui reçoit la valeur du champ et peut lire un autre champ avec valueOf : c'est ainsi qu'on fait un contrôle inter-champs. applyEach applique une règle à chaque élément d'un tableau, ce qui remplace le FormArray.

src/app/signal/signal-application.ts
export class SignalApplication {
  // le signal EST la source de vérité : le formulaire lit et écrit dedans
  readonly model = signal<HousingApplication>({
    lastName: '',
    email: '',
    confirmEmail: '',
    monthlyIncome: 0,
    address: { city: '', zip: '' },
    occupants: [],
  });
  readonly sent = signal(false);

  // 2. form(modèle, schéma) : toute la validation au même endroit
  readonly f = form(
    this.model,
    (p) => {
      required(p.lastName, { message: 'Le nom est obligatoire' });
      required(p.email, { message: "L'email est obligatoire" });
      email(p.email, { message: 'Email invalide' });
      // validateur personnalisé et inter-champs : on lit un autre champ avec valueOf
      validate(p.confirmEmail, ({ value, valueOf }) =>
        value() === valueOf(p.email) ? undefined : { kind: 'emailsMismatch', message: 'Les deux emails diffèrent' },
      );
      min(p.monthlyIncome, 1000, { message: 'Au moins 1000 €' });
      pattern(p.address.zip, /^\d{5}$/, { message: '5 chiffres attendus' });
      // un tableau du modèle : la même règle pour chaque élément
      applyEach(p.occupants, (o) => required(o.firstName, { message: 'Prénom obligatoire' }));
    },
    {
      // 3. l'envoi : lancé par [formRoot] seulement si le formulaire est valide
      submission: {
        action: async (field) => {
          console.log('[signal] envoyé', field().value());
          this.sent.set(true);
        },
      },
    },
  );

La liaison dans le template, et l'état d'un champ

[formField]="f.lastName" lie un élément natif à un champ. L'état d'un champ s'obtient en l'appelant : f.lastName() renvoie un objet de signals, value(), valid(), invalid(), errors(), touched(), dirty(). Les erreurs portent le message déclaré dans le schéma. Un tableau du modèle se parcourt directement avec @for.

src/app/signal/signal-application.ts
<form [formRoot]="f">
  <label>Nom <input [formField]="f.lastName" /></label>
  @if (f.lastName().touched() && f.lastName().invalid()) {
    @for (e of f.lastName().errors(); track e.kind) { <small class="error">{{ e.message }}</small> }
  }
  <label>Email <input type="email" [formField]="f.email" /></label>
  <label>Confirmer l'email <input [formField]="f.confirmEmail" /></label>
  @for (e of f.confirmEmail().errors(); track e.kind) { <small class="error">{{ e.message }}</small> }

  <label>Revenus mensuels <input type="number" [formField]="f.monthlyIncome" /></label>
  <label>Ville <input [formField]="f.address.city" /></label>
  <label>Code postal <input [formField]="f.address.zip" /></label>

  @for (occupant of f.occupants; track $index) {
    <label>Occupant {{ $index + 1 }} <input [formField]="occupant.firstName" /></label>
  }
  <button type="button" (click)="addOccupant()">Ajouter un occupant</button>
  <button type="submit">Envoyer</button>
</form>

Ajouter un occupant ne passe par aucune API de formulaire : on modifie le modèle, et l'arbre de champs suit.

src/app/signal/signal-application.ts
// ajouter un élément = modifier le modèle, le formulaire suit
addOccupant() {
  this.model.update((m) => ({ ...m, occupants: [...m.occupants, { firstName: '' }] }));
}

L'envoi : submit() et [formRoot]

[formRoot] pose novalidate sur <form>, empêche le rechargement de la page et appelle submit() avec l'action déclarée dans form(). submit() marque d'abord tous les champs comme touchés (les messages apparaissent), puis ne lance l'action que si le formulaire est valide. Deux différences visibles avec Reactive Forms. Les classes CSS ng-invalid / ng-touched ne sont pas posées par défaut (pour les retrouver : provideSignalFormsConfig avec NG_STATUS_CLASSES, de @angular/forms/signals/compat). En revanche, le schéma ajoute lui-même l'attribut required sur l'<input>.

Un formulaire en plusieurs étapes

Pour un dossier en plusieurs étapes, gardez un seul modèle et un seul form(), et ajoutez un signal step à part, qui dit seulement quelle étape afficher. La validité de l'étape courante se dérive avec un computed ; submit() vérifie à la fin le formulaire entier.

src/app/signal/signal-wizard.ts
export class SignalWizard {
  // UN seul modèle et UN seul form() pour toutes les étapes
  readonly model = signal<Dossier>({ firstName: '', emailAddress: '', employer: '', taxNumber: '' });
  readonly f = form(this.model, (p) => {
    required(p.firstName);
    required(p.emailAddress);
    email(p.emailAddress);
    required(p.employer);
    required(p.taxNumber);
    minLength(p.taxNumber, 13); // 13 chiffres
  });

  // l'étape courante : un signal SÉPARÉ, qui ne dit rien de la validité
  readonly step = signal(1);
  readonly sent = signal(false);

  // la validité de l'étape affichée, dérivée des champs de cette étape
  readonly currentStepValid = computed(() => {
    switch (this.step()) {
      case 1: return this.f.firstName().valid() && this.f.emailAddress().valid();
      case 2: return this.f.employer().valid() && this.f.taxNumber().valid();
      default: return true;
    }
  });

  next() { if (this.currentStepValid()) this.step.update((s) => s + 1); }
  prev() { this.step.update((s) => Math.max(1, s - 1)); }

  async send() {
    // submit() vérifie le formulaire ENTIER avant de lancer l'action
    await submit(this.f, async () => { this.sent.set(true); });
  }

Le template affiche les champs de l'étape courante, et le bouton « Suivant » suit currentStepValid().

6Formulaire dynamique, construit depuis un JSON

Certains formulaires ne sont pas connus à l'avance : un dossier dont les questions viennent d'une API ou d'un back-office. On ne peut plus écrire le template champ par champ. L'idée, celle d'un form builder, tient en quatre étapes : une description JSON, un modèle typé de « question », un service qui fabrique le FormGroup, et un template générique qui affiche chaque question selon son type.

1. Le modèle de question : des types, pas des classes

La documentation Angular décrit les questions avec une classe QuestionBase<T> et des sous-classes. On préfère ici des interfaces réunies en une union discriminée : le champ controlType dit de quelle question il s'agit. Deux raisons. Un JSON reçu est un objet brut, jamais une instance de classe (le piège vu dans la démo HTTP, section 4) : avec des interfaces, il n'y a rien à construire. Et l'union permet à TypeScript de savoir, après un test sur controlType, que la question a des options ou un min.

src/app/dynamic/question.ts
// La description d'UNE question, telle qu'elle arrive en JSON.
// Des types (pas des classes) : un JSON reçu est un objet brut, jamais une instance.

interface QuestionCommon {
  key: string; // le nom du contrôle dans le FormGroup
  label: string;
  required?: boolean;
  order: number;
}

export interface TextQuestion extends QuestionCommon {
  controlType: 'text';
  minLength?: number;
  pattern?: string; // une RegExp écrite en chaîne, puisque le JSON n'a pas de RegExp
  value?: string;
}

export interface NumberQuestion extends QuestionCommon {
  controlType: 'number';
  min?: number;
  max?: number;
  value?: number;
}

export interface SelectQuestion extends QuestionCommon {
  controlType: 'select';
  options: { key: string; label: string }[];
  value?: string;
}

export interface CheckboxQuestion extends QuestionCommon {
  controlType: 'checkbox';
  value?: boolean;
}

// L'union discriminée : controlType dit de quelle question il s'agit.
export type Question = TextQuestion | NumberQuestion | SelectQuestion | CheckboxQuestion;

3. Le service : de la configuration au FormGroup

Le service parcourt les questions et crée un FormControl par question, avec ses validateurs déduits de la configuration. Le switch sur controlType est exactement l'endroit où l'union discriminée sert : dans le cas 'number', TypeScript sait que q.min existe.

src/app/dynamic/question-control.service.ts
import { Injectable } from '@angular/core';
import { FormControl, FormGroup, ValidatorFn, Validators } from '@angular/forms';
import { Question } from './question';

@Injectable({ providedIn: 'root' })
export class QuestionControlService {
  // la configuration => un FormGroup, un FormControl par question
  toFormGroup(questions: Question[]): FormGroup {
    const controls: Record<string, FormControl> = {};
    for (const q of questions) {
      controls[q.key] = new FormControl(q.value ?? null, this.validatorsFor(q));
    }
    return new FormGroup(controls);
  }

  // les règles du JSON => les validateurs Angular
  private validatorsFor(q: Question): ValidatorFn[] {
    const validators: ValidatorFn[] = [];
    if (q.required) {
      validators.push(q.controlType === 'checkbox' ? Validators.requiredTrue : Validators.required);
    }
    switch (q.controlType) {
      case 'text':
        if (q.minLength) validators.push(Validators.minLength(q.minLength));
        if (q.pattern) validators.push(Validators.pattern(q.pattern));
        break;
      case 'number':
        if (q.min !== undefined) validators.push(Validators.min(q.min));
        if (q.max !== undefined) validators.push(Validators.max(q.max));
        break;
    }
    return validators;
  }
}

La classe se résume au tri, à la construction du groupe et à un message lisible par type d'erreur.

src/app/dynamic/dynamic-form.ts
export class DynamicForm {
  readonly questions = input.required<Question[]>();
  private readonly qcs = inject(QuestionControlService);

  readonly sorted = computed(() => [...this.questions()].sort((a, b) => a.order - b.order));
  // le FormGroup est reconstruit si la configuration change
  readonly form = computed(() => this.qcs.toFormGroup(this.questions()));
  payload: unknown = null;

  // un message lisible par erreur (les clés sont celles des validateurs Angular)
  messageFor(errors: ValidationErrors | null): string {
    if (!errors) return '';
    if (errors['required']) return 'Champ obligatoire';
    if (errors['min']) return `Minimum ${errors['min'].min}`;
    if (errors['minlength']) return `${errors['minlength'].requiredLength} caractères minimum`;
    if (errors['pattern']) return 'Format invalide';
    return 'Valeur invalide';
  }
}

La même idée avec Signal Forms

Elle fonctionne aussi : le modèle initial se calcule depuis le JSON (une valeur par question), et le schéma est écrit en parcourant la configuration. Mais le typage, point fort de Signal Forms, se perd : avec un Record<string, string | number | boolean>, le compilateur refuse de lier un <input type="number"> à un champ qui pourrait être une chaîne. Il faut redonner le type à la main, comme le montrent les trois dernières méthodes.

src/app/dynamic/dynamic-signal-form.ts
type Answers = Record<string, string | number | boolean>;

// la configuration => le modèle initial (une valeur par question)
function initialAnswers(questions: Question[]): Answers {
  const defaults = { text: '', number: 0, select: '', checkbox: false };
  return Object.fromEntries(questions.map((q) => [q.key, q.value ?? defaults[q.controlType]]));
}
// ...
export class DynamicSignalForm {
  readonly questions = [...HOUSING_DOSSIER].sort((a, b) => a.order - b.order);
  readonly model = signal<Answers>(initialAnswers(this.questions));

  // le schéma est écrit en parcourant la configuration
  readonly f = form(this.model, (p) => {
    for (const q of this.questions) {
      if (q.required) required(p[q.key]);
      if (q.controlType === 'text' && q.pattern) {
        pattern(p[q.key] as SchemaPath<string>, new RegExp(q.pattern));
      }
      if (q.controlType === 'number' && q.min !== undefined) {
        min(p[q.key] as SchemaPath<number>, q.min);
      }
    }
  });

  // le prix du dynamique : Record<string, mixte> perd le type de chaque champ,
  // il faut le redonner à la main pour que [formField] accepte la liaison
  asText(key: string) { return this.f[key] as FieldTree<string>; }
  asNumber(key: string) { return this.f[key] as FieldTree<number>; }
  asBoolean(key: string) { return this.f[key] as FieldTree<boolean>; }
}

Vérifié : ce composant compile, et le modèle passe à valid = true avec les mêmes valeurs que la version Reactive. Pour un formulaire entièrement piloté par une configuration, Reactive Forms reste aujourd'hui l'écriture la plus directe ; Signal Forms brille quand la forme des données est connue à la compilation.

À retenir JSON => un type Question (union discriminée par controlType) => un service qui fabrique le FormGroup => un template générique @for + @switch. Des interfaces plutôt que des classes, car le JSON reste un objet brut. Ajouter une question = ajouter une ligne au JSON.

7Choisir, et migrer

Le bon choix dépend surtout de la version du projet : Signal Forms n'existe pas en v20. Le tableau suivant donne un choix par défaut pour les situations les plus courantes.

SituationNouveau projet v22Projet existant en v20
Formulaire simple (contact, recherche, 2 ou 3 champs)Signal Formstemplate-driven ou Reactive Forms
Formulaire complexe (groupes imbriqués, validations croisées, listes)Signal Forms : schéma, validate, applyEachReactive Forms typés, NonNullableFormBuilder
Formulaire dynamique, construit depuis un JSONReactive Forms (section 6), ou Signal Forms en acceptant des conversions de typeReactive Forms
Dossier en plusieurs étapesSignal Forms : un modèle, un form(), un signal stepReactive Forms : un FormGroup par étape dans un groupe parent
Formulaires Reactive déjà en placeles garder, migrer au fil de l'eau (ci-dessous)les garder ; monter de version avant de penser Signal Forms

La migration de Reactive Forms vers Signal Forms se fait progressivement, formulaire par formulaire, et la documentation fournit des outils de cohabitation dans @angular/forms/signals/compat.

  1. Passer en v22 avec ng update : en v21, l'API est encore expérimentale et ses noms ont changé.
  2. Écrire les nouveaux formulaires en Signal Forms, sans toucher aux anciens.
  3. Migrer par les feuilles : SignalFormControl se comporte comme un FormControl dans un FormGroup existant, et se lie avec [formField]="control.fieldTree".
  4. Ou par le haut : compatForm crée un formulaire Signal Forms dont le modèle contient encore des FormControl existants, le temps de les porter.
  5. Remplacer l'impératif par du déclaratif : enable(), disable(), setValidators() deviennent des règles du schéma (disabled, applyWhen, validateurs).
  6. Adapter les composants de saisie maison : un ControlValueAccessor devient un FormValueControl, et NG_STATUS_CLASSES restaure les classes ng-invalid si votre CSS en dépend.

Ces noms existent dans les types installés de @angular/forms 22.2.2 (@publicApi 22.0), mais ils n'ont pas été exercés dans le projet de vérification : suivez le guide de migration pour leur usage exact.

Pour pratiquer : le tutoriel Housing, premiers pas construit, à son étape 18, un dossier de candidature en plusieurs étapes en Reactive Forms ; le parcours avancé Housing sous pression asynchrone le migre vers Signal Forms.

À retenir En v22, Signal Forms par défaut pour un nouveau formulaire ; Reactive Forms pour un formulaire entièrement piloté par une configuration, et pour tout projet v20. Template-driven reste possible pour quelques champs. On migre sans tout réécrire : nouveaux formulaires d'abord, puis les anciens, contrôle par contrôle.
