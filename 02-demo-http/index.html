Tout ce qui est global à l'application se déclare dans app.config.ts, sous forme de providers. ng new y met provideBrowserGlobalErrorListeners(), qui fait remonter à Angular les erreurs non attrapées du navigateur, et provideRouter(routes) ; la démo y ajoute la liaison des paramètres de route (section 2) et les intercepteurs (section 8).

src/app/app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    // withComponentInputBinding : les paramètres de route arrivent dans les input()
    provideRouter(routes, withComponentInputBinding()),
    // ordre = ordre de passage de la requête (et ordre inverse pour la réponse)
    provideHttpClient(withInterceptors([loggingInterceptor, authInterceptor, errorInterceptor])),
  ],
};
À retenir Un projet se crée avec ng new et se lance avec npm start. En v22, un projet neuf est standalone (chaque composant déclare ses propres imports, sans module), zoneless, testé avec Vitest et sans SSR. La configuration globale vit dans app.config.ts : les projets plus anciens la mettaient dans un AppModule.

2Routing

Le routeur associe une URL à un composant. La démo a deux écrans principaux : la liste /produits et le détail /produits/:id, où :id est un paramètre qui change à chaque produit.

Les routes sont déclarées dans app.routes.ts. Toutes utilisent loadComponent : le composant est placé dans un fichier JavaScript à part (un chunk), téléchargé seulement à la première visite de la route.

src/app/app.routes.ts
export const routes: Routes = [
  { path: '', pathMatch: 'full', redirectTo: 'produits' },
  // loadComponent : le code du composant n'est téléchargé qu'à la première visite
  { path: 'produits', loadComponent: () => import('./products/product-list').then((m) => m.ProductList) },
  { path: 'produits/:id', loadComponent: () => import('./products/product-detail').then((m) => m.ProductDetail) },
  { path: 'produits-signals', loadComponent: () => import('./products/product-list-signals').then((m) => m.ProductListSignals) },
  { path: 'bases', loadComponent: () => import('./pages/http-basics').then((m) => m.HttpBasics) },
  { path: 'connexion', loadComponent: () => import('./pages/login').then((m) => m.Login) },
  { path: '**', redirectTo: 'produits' },
];

Reste à lire l':id dans le composant de détail. La démo le lit de deux façons, affichées côte à côte. La façon moderne : grâce à withComponentInputBinding() dans provideRouter (section 1), le paramètre arrive directement dans un input() du même nom. La façon classique : injecter ActivatedRoute, le service qui décrit la route active. Son paramMap est un Observable (un flux de valeurs, présenté en section 3), que toSignal transforme en signal.

src/app/products/product-detail.ts
export class ProductDetail {
  private readonly products = inject(ProductsService);
  private readonly route = inject(ActivatedRoute);

  // 1. withComponentInputBinding() : le :id de l'URL arrive dans cet input()
  readonly id = input.required({ transform: numberAttribute });

  // 2. la méthode classique, ActivatedRoute
  readonly idFromParamMap = toSignal(this.route.paramMap.pipe(map((params) => Number(params.get('id')))));
  readonly idFromSnapshot = Number(this.route.snapshot.paramMap.get('id')); // figé à la création

Le schéma suivant résume le trajet complet, de l'URL tapée jusqu'à l'input() rempli.

La différence se voit quand on change d'id sans quitter l'écran. Le lien « Produit suivant » de la démo passe de 11 à 12 : Angular réutilise le composant au lieu d'en créer un nouveau, et voici ce qu'il affiche alors.

Pour lire un paramètre, il vaut mieux withComponentInputBinding() + input() : c'est un signal, toujours à jour. Un paramètre d'URL est une chaîne, d'où numberAttribute pour obtenir un nombre. Le snapshot est à éviter dès qu'on peut naviguer d'un id à l'autre sur le même écran.

3HttpClient

HttpClient est le service Angular qui fait les appels HTTP. Il renvoie des Observables RxJS : un Observable est un flux de valeurs auquel on s'abonne pour les recevoir ; pour un appel HTTP, le flux émet une seule valeur (la réponse) puis se termine. Par convention, le nom d'une variable qui contient un Observable finit par $. Chaque requête traverse aussi les intercepteurs (section 8) avant de partir sur le réseau.

Depuis Angular 21, HttpClient est injectable sans rien déclarer : provideHttpClient() ne sert plus qu'à le configurer, ici pour brancher les intercepteurs (voir app.config.ts en section 1). Sur un projet v20, il reste obligatoire. Autre point à connaître en v22 : les requêtes passent par défaut par l'API fetch du navigateur, et withFetch() est marqué déprécié. Pour revenir à XMLHttpRequest, par exemple pour suivre la progression d'un envoi de fichier (que fetch ne remonte pas), on ajoute withXhr().

Un appel se déclare avec get<T>(url). Point clé : un Observable HTTP est froid, déclarer product$ n'envoie rien, la requête part à chaque abonnement. La page « Bases HttpClient » de la démo s'abonne volontairement deux fois au même Observable, une fois avec toSignal et une fois avec subscribe.

src/app/pages/http-basics.ts
export class HttpBasics {
  private readonly http = inject(HttpClient);
// ...

  // un Observable HTTP est FROID : rien ne part tant que personne ne s'abonne,
  // et CHAQUE abonnement relance la requête (ici : 2 abonnements => 2 requêtes)
  private readonly product$ = this.http.get<Product>(`${environment.apiUrl}/products/1`);

  // abonnement n°1 : toSignal s'abonne, et se désabonne à la destruction du composant
  readonly product = toSignal(this.product$);

  constructor() {
    // abonnement n°2 : subscribe à la main, takeUntilDestroyed coupe à la destruction
    this.product$
      .pipe(takeUntilDestroyed())
      .subscribe((p) => console.log('[bases] reçu par subscribe :', p.title));
  }

httpResource, la version signals

Pour une lecture pilotée par des signals, Angular 22 propose httpResource : apparue en v19.2 comme expérimentale, elle est stable en v22 (les types installés la marquent @publicApi 22.0). On lui donne une fonction qui construit la requête ; quand un signal lu dans cette fonction change, la requête repart et la précédente est annulée. La démo affiche la même liste paginée des deux façons, dans les écrans « Produits (RxJS) » et « Produits (httpResource) ». Les deux appellent le service de produits, dont les méthodes list() et listResource() sont construites aux sections 5 et 6.

src/app/products/product-list.ts
  readonly limit = 10;
  readonly skip = signal(0);

  // skip change => nouvelle requête ; switchMap annule celle qui n'est pas finie
  readonly page = toSignal(
    toObservable(this.skip).pipe(switchMap((skip) => this.products.list(skip, this.limit))),
  );

« Produits (RxJS) » : toObservable transforme le signal skip en Observable, switchMap lance une requête par valeur et annule la précédente, toSignal revient aux signals.

src/app/products/product-list-signals.ts
  readonly limit = 10;
  readonly skip = signal(0);
  private readonly params = computed(() => ({ skip: this.skip(), limit: this.limit }));

  // params change => httpResource relance la requête (et annule la précédente)
  readonly page = inject(ProductsService).listResource(this.params);

« Produits (httpResource) » : params change, la requête repart. listResource est une fabrique du service générique (section 6).

Une resource expose son état sous forme de signals : value(), hasValue(), isLoading(), error(), et reload() pour relancer. Attention, value() lève une erreur si la resource est en erreur : testez hasValue() avant, comme le fait le template de la démo. Et httpResource ne sert qu'à lire : les écritures (POST, PATCH, DELETE) restent des appels HttpClient, déclenchés par une action de l'utilisateur.

À retenir On injecte HttpClient, puis on déclare l'appel avec get<T>(url). Rien ne part tant que personne ne s'abonne, et chaque abonnement relance la requête. toSignal pour afficher, subscribe + takeUntilDestroyed pour un effet, httpResource pour une lecture qui suit des signals.

4Typer les réponses

Le <T> de get<T>() est une promesse faite au compilateur, pas une conversion : le JSON reçu reste un objet JavaScript brut, et rien ne vérifie qu'il a la forme annoncée. Pour décrire cette forme, une interface (ou un type) suffit, et elle ne coûte rien au bundle puisqu'elle disparaît à la compilation.

Le fichier product.ts de la démo contient les deux cas : l'interface Product pour le JSON, et une classe ProductModel, justifiée parce qu'elle porte un vrai comportement (le calcul du prix remisé).

src/app/products/product.ts
// Ce que l'API renvoie : une INTERFACE décrit la forme du JSON, sans rien créer.
export interface Product {
  id: number;
  title: string;
  description: string;
  category: string;
  price: number;
  discountPercentage: number;
  rating: number;
  stock: number;
  thumbnail: string;
}

// Une CLASSE seulement si on a un vrai comportement à porter.
// Elle ne se remplit jamais toute seule : il faut la construire (fromJson).
export class ProductModel {
  constructor(
    readonly id: number,
    readonly title: string,
    readonly price: number,
    readonly discountPercentage: number,
  ) {}

  static fromJson(json: Product): ProductModel {
    return new ProductModel(json.id, json.title, json.price, json.discountPercentage);
  }

  discountedPrice(): number {
    return Math.round(this.price * (1 - this.discountPercentage / 100) * 100) / 100;
  }
}

Le piège classique consiste à demander get<ProductModel>() : le code compile, mais l'objet reçu n'est pas une instance de la classe. L'écran « Bases HttpClient » de la démo met les deux écritures face à face, dans le tableau « Le piège de la classe ».

src/app/pages/http-basics.ts
  // PIÈGE : le <ProductModel> ne construit rien, c'est une promesse faite au compilateur
  readonly wrong = toSignal(this.http.get<ProductModel>(`${environment.apiUrl}/products/2`));
  readonly wrongIsInstance = computed(() => this.wrong() instanceof ProductModel); // false
  readonly wrongMethodType = computed(() => typeof this.wrong()?.discountedPrice); // 'undefined'

  // CORRECT : on reçoit l'interface, puis on construit l'instance explicitement
  readonly right = toSignal(
    this.http.get<Product>(`${environment.apiUrl}/products/2`).pipe(map(ProductModel.fromJson)),
  );
  readonly rightIsInstance = computed(() => this.right() instanceof ProductModel); // true
  readonly rightMethodType = computed(() => typeof this.right()?.discountedPrice); // 'function'

Voici ce que la démo affiche pour le produit 2.

get<ProductModel>()get<Product>() + map(ProductModel.fromJson)

discountedPrice()TypeError à l'appel16.35
À retenir Une interface ou un type pour décrire le JSON. Une classe seulement s'il y a du comportement, et alors on la construit explicitement (map(ProductModel.fromJson)), de préférence dans le service. Même logique pour les dates : le JSON les apporte en chaînes, jamais en Date.

5Une enveloppe générique, Page<T>

Une API renvoie rarement un tableau nu : la liste arrive dans une enveloppe qui porte aussi la pagination. Chez dummyjson, la clé du tableau change selon la ressource, comme le montrent ces trois appels.

$ curl 'https://dummyjson.com/products?limit=2&skip=0&select=title,price'
{"products":[{"id":1,"title":"Essence Mascara Lash Princess","price":9.99},{"id":2,"title":"Eyeshadow Palette with Mirror","price":19.99}],"total":194,"skip":0,"limit":2}
$ curl 'https://dummyjson.com/users?limit=1&select=firstName'
{"users":[{"id":1,"firstName":"Emily"}],"total":208,"skip":0,"limit":1}
$ curl 'https://dummyjson.com/carts?limit=1&select=id'
{"carts":[{"id":1}],"total":208,"skip":0,"limit":1}

Plutôt que de laisser chaque composant connaître products, users ou carts, on définit notre propre forme, Page<T>, la même pour toutes les ressources, et un adaptateur qui transforme l'enveloppe de l'API en Page<T>. Le T est un paramètre de type : Page<Product> est une page de produits, Page<User> une page d'utilisateurs, avec le même code. toPage('products') fabrique la fonction de conversion adaptée à la clé products.

src/app/core/page.ts
// La forme BRUTE renvoyée par dummyjson pour une liste :
// { products: [...], total, skip, limit }, { users: [...], ... }, { carts: [...], ... }
// La clé du tableau change selon la ressource, d'où le paramètre K.
export type DummyJsonList<K extends string, T> = Record<K, T[]> & {
  total: number;
  skip: number;
  limit: number;
};

// NOTRE forme, identique pour toutes les ressources : c'est elle que voient les composants.
export interface Page<T> {
  items: T[];
  total: number;
  skip: number;
  limit: number;
}

// L'adaptateur : transforme l'enveloppe dummyjson en Page<T>.
export function toPage<K extends string, T>(key: K) {
  return (raw: DummyJsonList<K, T>): Page<T> => ({
    items: raw[key],
    total: raw.total,
    skip: raw.skip,
    limit: raw.limit,
  });
}

Le schéma suivant montre la transformation sur la liste des produits.

L'adaptateur est appliqué une seule fois, dans le service, avec l'opérateur map de RxJS. La clé de l'enveloppe est le nom de la ressource (endpoint), ce qui permet au même code de servir pour products, users ou carts.

src/app/core/resource.service.ts
  // --- Observables ---
  list(skip = 0, limit = 10): Observable<Page<T>> {
    return this.http
      .get<DummyJsonList<string, T>>(this.url(), { params: { skip, limit } })
      .pipe(map(toPage<string, T>(this.endpoint))); // on déballe ICI, une seule fois
  }

Le composant « Produits (RxJS) », déjà vu en section 3, ne manipule donc que des Page<Product> : il ne sait pas que l'API s'appelle dummyjson, et la pagination se résume à changer skip, avec deux méthodes.

src/app/products/product-list.ts
export class ProductList {
  private readonly products = inject(ProductsService);
  readonly limit = 10;
  readonly skip = signal(0);
  // ...
  previous() { this.skip.update((s) => Math.max(0, s - this.limit)); }
  next() { this.skip.update((s) => s + this.limit); }
}

Reste à choisir où déballer l'enveloppe. Il y a trois candidats, et le service est le bon compromis.

OùPourContre
Dans le composantrien à écrire au départchaque composant répète le code et dépend du format de l'API
Dans le serviceun seul endroit, typé de bout en bout, les composants ignorent l'APIun map par méthode (ici factorisé par le service générique)
Dans un intercepteurtraite toutes les réponses d'un coupinvisible depuis le service : le <T> de get<T>() décrit une forme que rien ne garantit, et l'intercepteur touche aussi les réponses qui n'ont pas cette enveloppe

L'intercepteur ne se justifie que si toute l'API utilise la même enveloppe, par exemple { data, meta }. Ce cas se modélise avec le même principe : un type ApiResponse<T> et un map(r => r.data), de préférence dans le service.

À retenir Les composants ne doivent pas connaître le format de l'API. Un type générique à vous (Page<T>, ApiResponse<T>), un adaptateur, et un map dans le service : si l'API change, un seul fichier bouge.

6Un service générique, ResourceService<I, T>

Avec plusieurs ressources (produits, utilisateurs, paniers), les services se ressemblent tous : même forme d'URL, même enveloppe, mêmes méthodes. On écrit ce code une fois, dans une classe abstraite et générique, paramétrée par le type de l'id I et le type de la ressource T.

src/app/core/resource.service.ts
// Service CRUD générique : I = type de l'id, T = type de la ressource.
// - Observables pour tout ce qui est appelé à la demande (lectures ET mutations),
//   pour pouvoir composer avec RxJS (switchMap, exhaustMap, retry...).
// - Fabriques httpResource pour les lectures pilotées par des signals.
export abstract class ResourceService<I, T> {
  protected readonly http = inject(HttpClient);
  private readonly baseUrl = environment.apiUrl;

  // endpoint = 'products' : sert à la fois pour l'URL et pour la clé de l'enveloppe
  constructor(protected readonly endpoint: string) {}

  protected url(path = ''): string {
    return `${this.baseUrl}/${this.endpoint}${path}`;
  }

  // --- Observables ---
  list(skip = 0, limit = 10): Observable<Page<T>> {
    return this.http
      .get<DummyJsonList<string, T>>(this.url(), { params: { skip, limit } })
      .pipe(map(toPage<string, T>(this.endpoint))); // on déballe ICI, une seule fois
  }

  get(id: I): Observable<T> {
    return this.http.get<T>(this.url(`/${id}`));
  }

  // dummyjson simule les écritures : la réponse est correcte, rien n'est enregistré
  create(item: Partial<T>): Observable<T> {
    return this.http.post<T>(this.url('/add'), item); // dummyjson : POST /products/add
  }

  patch(id: I, changes: Partial<T>): Observable<T> {
    return this.http.patch<T>(this.url(`/${id}`), changes);
  }

  // --- Fabriques httpResource (lecture seule, réactives) ---
  listResource(params: Signal<{ skip: number; limit: number }>) {
    return httpResource<Page<T>>(() => ({ url: this.url(), params: params() }), {
      parse: (raw) => toPage<string, T>(this.endpoint)(raw as DummyJsonList<string, T>),
    });
  }

  oneResource(id: Signal<I>) {
    return httpResource<T>(() => this.url(`/${id()}`));
  }
}

Chaque ressource devient alors une sous-classe de trois lignes utiles. Pour les utilisateurs, on écrirait la même chose avec un type User et l'endpoint 'users'.

Une variante courante de ce service renvoie des Promise pour les écritures (avec firstValueFrom). On garde ici des Observables, parce qu'une écriture se compose avec les opérateurs RxJS. Le bouton « Baisser le prix » du détail passe par exhaustMap, qui ignore les clics tant que la requête PATCH n'est pas revenue. Avec une Promise, la requête est déjà partie au moment de l'appel : on ne peut plus l'annuler, et pour ignorer les clics suivants il faut coder soi-même (un drapeau, un bouton désactivé) ce qu'exhaustMap fait en un opérateur. Le clic du template envoie le prix courant dans un Subject, un Observable dans lequel on pousse soi-même des valeurs avec next().

src/app/products/product-detail.ts
      <button (click)="discount$.next(p.price)">Baisser le prix de 10 % (PATCH simulé)</button>

Dans la classe, ce flux de clics passe par exhaustMap avant d'appeler patch(), et la réponse remplace la valeur de la resource du détail.

src/app/products/product-detail.ts
  // lecture réactive : id change => la requête repart
  readonly product = this.products.oneResource(this.id);

  // mutation : Observable + exhaustMap => les clics pendant la requête sont ignorés
  protected readonly discount$ = new Subject<number>();

  constructor() {
    this.discount$
      .pipe(
        exhaustMap((price) => this.products.patch(this.id(), { price: Math.round(price * 90) / 100 })),
        takeUntilDestroyed(),
      )
      .subscribe((updated) => this.product.set(updated));
  }

Trois clics rapides dans la démo ne produisent qu'un seul PATCH (le GET qui le précède est le chargement du détail), et le prix affiché passe de $2,499.99 à $2,249.99.

[HTTP] GET https://dummyjson.com/products/12 -> 200 en 117 ms
[HTTP] PATCH https://dummyjson.com/products/12 -> 200 en 121 ms

⚖️ Deux choix à connaître. D'abord, dans le service générique, la clé de l'enveloppe est une simple string (l'endpoint) : le type DummyJsonList<string, T> ne vérifie donc plus le nom de la clé, c'est le prix de la généricité. Ensuite, le service lit environment.apiUrl directement. C'est simple dans une application, mais une bibliothèque (une lib Nx, par exemple) ne peut pas importer l'environnement de l'application qui l'utilise : il vaut mieux alors un InjectionToken (API_URL) que l'application fournit dans app.config.ts. Le parcours avancé, avec le lab Housing sous pression asynchrone, construit ce même service générique plus tard.

À retenir Le code commun vit dans une classe abstraite ResourceService<I, T>, et chaque ressource n'est qu'une sous-classe de trois lignes. Des Observables pour tout ce qu'on déclenche (et qu'on veut composer avec switchMap, exhaustMap…), des fabriques httpResource pour les lectures pilotées par des signals.

7Environnements

L'URL de l'API n'est pas la même sur le poste du développeur, en recette et en production. Angular gère cela avec des fichiers d'environnement, remplacés au moment du build. Un projet neuf n'en a pas : on les génère avec une commande du CLI.

$ npx ng generate environments
CREATE src/environments/environment.ts (31 bytes)
CREATE src/environments/environment.development.ts (31 bytes)
UPDATE angular.json (2122 bytes)

Les deux fichiers exportent le même objet, avec les mêmes clés. La démo y met apiUrl, et un name affiché dans l'en-tête de l'application pour voir lequel est actif.

src/environments/environment.ts
// Utilisé par `ng build` (configuration production, celle par défaut du build).
// Tout ce qui est ici finit EN CLAIR dans le bundle JS : aucun secret.
export const environment = {
  name: 'production',
  apiUrl: 'https://dummyjson.com',
};
src/environments/environment.development.ts
// Utilisé par `ng serve` : angular.json remplace environment.ts par ce fichier
// (fileReplacements de la configuration development).
export const environment = {
  name: 'development',
  apiUrl: 'https://dummyjson.com',
};

Le remplacement est écrit dans angular.json, dans la configuration development du build : à la compilation, chaque import de environment.ts pointe en fait sur environment.development.ts.

Un fichier d'environnement n'est pas un coffre-fort : tout ce qu'il contient, et plus généralement tout ce que le code importe, finit en clair dans le JavaScript téléchargé par le navigateur. La démo le prouve avec le faux jeton de l'intercepteur d'authentification (section 8), retrouvé tel quel dans le bundle de production.

$ grep -o 'faux-jeton-de-demo' dist/demo/browser/*.js
dist/demo/browser/main-IB3VI3I3.js:faux-jeton-de-demo

Enfin, les fichiers .env ne sont pas le mécanisme Angular : le CLI ne les lit pas pour les injecter dans l'application. Pour une valeur fournie par le pipeline de CI au moment du build, on génère le fichier d'environnement dans le pipeline, ou on utilise l'option define d'angular.json, qui remplace un identifiant global par une constante (valeur écrite entre guillemets JSON, identifiant déclaré avec declare const). Pour construire une seule fois et déployer le même bundle partout, il faut une configuration lue à l'exécution : un config.json servi avec l'application et chargé au démarrage, par exemple avec provideAppInitializer.

À retenir ng generate environments crée deux fichiers aux clés identiques, et fileReplacements choisit lequel utiliser au build. On y met des URL et des options, jamais de secret : un front n'a pas de secret, tout est lisible dans le bundle.

8Intercepteurs fonctionnels

Un intercepteur est une fonction placée entre HttpClient et le réseau : chaque requête la traverse à l'aller, chaque réponse au retour. C'est l'endroit pour tout ce qui concerne tous les appels : journaliser, authentifier, gérer les erreurs.

Les intercepteurs se déclarent dans app.config.ts. L'ordre du tableau est l'ordre de passage de la requête ; la réponse repasse dans l'ordre inverse.

src/app/app.config.ts
    // ordre = ordre de passage de la requête (et ordre inverse pour la réponse)
    provideHttpClient(withInterceptors([loggingInterceptor, authInterceptor, errorInterceptor])),

Le schéma suivant montre le trajet aller et retour à travers les trois intercepteurs de la démo.

1. Journaliser avec la durée

Le premier intercepteur note l'heure de départ, puis écrit une ligne quand la réponse arrive. Il ne modifie rien : il se contente d'observer le flux avec tap.

src/app/core/interceptors/logging.interceptor.ts
// Journalise chaque requête avec son statut et sa durée.
export const loggingInterceptor: HttpInterceptorFn = (req, next) => {
  const started = performance.now();
  const elapsed = () => Math.round(performance.now() - started);

  return next(req).pipe(
    tap({
      next: (event) => {
        if (event.type === HttpEventType.Response) {
          console.log(`[HTTP] ${req.method} ${req.urlWithParams} -> ${event.status} en ${elapsed()} ms`);
        }
      },
      error: (err: HttpErrorResponse) =>
        console.warn(`[HTTP] ${req.method} ${req.urlWithParams} -> ${err.status} en ${elapsed()} ms`),
    }),
  );
};

Dans la console de la démo, la pagination de la liste donne ces lignes.

[HTTP] GET https://dummyjson.com/products?skip=0&limit=10 -> 200 en 236 ms
[HTTP] GET https://dummyjson.com/products?skip=10&limit=10 -> 200 en 110 ms

2. Ajouter Authorization: Bearer

Une HttpRequest est immuable : pour ajouter un en-tête, on la clone. Le test sur l'URL évite d'envoyer le jeton à un autre domaine. Le jeton de la démo est une constante volontairement fausse ; dans une vraie application, il vient d'un service d'authentification après la connexion.

src/app/core/interceptors/auth.interceptor.ts
// FAUX JETON, POUR LA DÉMO UNIQUEMENT. Dans une vraie app, le jeton vient d'un
// AuthService (après connexion), jamais d'une constante dans le code.
export const FAKE_DEMO_TOKEN = 'faux-jeton-de-demo';

// Ajoute l'en-tête Authorization aux appels vers NOTRE API, et à eux seuls
// (le "/" final évite qu'un domaine comme dummyjson.com.autre.io passe le test).
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (!req.url.startsWith(`${environment.apiUrl}/`)) {
    return next(req);
  }
  // une HttpRequest est immuable : on la clone avec l'en-tête en plus
  const authReq = req.clone({ setHeaders: { Authorization: `Bearer ${FAKE_DEMO_TOKEN}` } });
  return next(authReq);
};

Dans la démo, les requêtes vers dummyjson partent bien avec l'en-tête Authorization: Bearer faux-jeton-de-demo, le GET du détail comme le PATCH du bouton. L'API publique l'ignore, sauf sur ses routes d'authentification, ce qui sert au troisième exemple.

3. Gérer les erreurs au même endroit

Le dernier intercepteur attrape les erreurs avec catchError. Un 401 (jeton absent ou expiré) envoie vers l'écran de connexion ; les autres erreurs sont journalisées. Dans tous les cas, l'erreur est relancée pour que le composant puisse encore réagir.

src/app/core/interceptors/error.interceptor.ts
// Gestion d'erreur centralisée : un seul endroit décide quoi faire d'un 401.
export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router); // inject() fonctionne dans un intercepteur fonctionnel

  return next(req).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) {
        router.navigate(['/connexion']); // jeton absent ou expiré => écran de connexion
      } else {
        console.error(`[HTTP] erreur ${err.status} sur ${req.url} :`, err.error?.message ?? err.message);
      }
      return throwError(() => err); // on relance : l'appelant peut encore réagir
    }),
  );
};

La page « Bases HttpClient » provoque les deux cas. Le bouton 401 appelle /auth/me avec le faux jeton, et l'application arrive sur /connexion. Le bouton 404 donne ces lignes, dans cet ordre : error écrit avant logging, parce que la réponse remonte la chaîne à l'envers.

[HTTP] erreur 404 sur https://dummyjson.com/products/99999 : Product with id '99999' not found
[HTTP] GET https://dummyjson.com/products/99999 -> 404 en 116 ms

Dans les projets plus anciens, vous croiserez des intercepteurs en classe (implements HttpInterceptor), déclarés avec le jeton HTTP_INTERCEPTORS et activés par withInterceptorsFromDi(). Ils fonctionnent encore, mais la documentation recommande les intercepteurs fonctionnels, à l'ordre plus prévisible, et prévient que le support des classes pourrait disparaître.

À retenir Un intercepteur est une fonction (req, next) => next(req) de type HttpInterceptorFn, déclarée dans withInterceptors([...]). L'ordre du tableau compte. On ne modifie pas une requête, on la clone. inject() fonctionne à l'intérieur, ce qui donne accès au Router ou à un service.
